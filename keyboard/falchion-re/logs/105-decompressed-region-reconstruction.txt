WHY THIS STEP EXISTS
Phase 3 recovered Candidate A's __scatterload region table and found one region
whose handler is __scatterload_decompress: flash 0x3f380 (0x400 compressed
bytes) -> RAM 0x1801e380 (0xb04 bytes). Those 0xb04 bytes exist in no dump. Log
104 named this as 5A's blind spot in as many words: "a callback ... held in the
decompressed region that is mapped but not reconstructed, cannot appear". This
step removes the blind spot.


STEP 1 — THE DECODER IS A TRANSLATION OF THE FIRMWARE'S OWN HANDLER
Added tool/reconstruct_decompress.py. The decoder is a direct translation of
the 0x5c bytes at Candidate A program offset 0x17c..0x1d8 that the scatter
descriptor names — the instruction sequence recovered in log 73 — not of a
generic ARM library routine. The module carries the sha256 of those exact bytes
and refuses to decode against a handler that does not hash to them.

  handler span   Candidate A program 0x17c..0x1d8 (0x5c bytes)
  handler sha256 582c480472872687b56e13f46ba6bbfb754d0449964344206bb23def06f56ae0

STATED EXPLICITLY: those handler bytes are BYTE-IDENTICAL in the preserved
vendor 1.00.58 image and the installed 1.59 readback. Both releases report the
same handler_sha256 above. That is why one implementation covers both, and it
is a measured fact in this run's output rather than an assumption.

Three decoding rules are worth naming because each was read off an instruction
and each would be wrong under a generic guess:
  - `subs r4,r4,#1` runs before the literal loop, so a literal field of N emits
    N-1 bytes, not N.
  - the back-reference loop is `add r5,#2` then a byte-at-a-time `strb`, so it
    emits field+2 bytes and an OVERLAPPING reference repeats what it just wrote.
  - with bit 3 clear the copy field is a count of zero bytes, not a copy.

ON THE ONE CHECK THAT WAS RESTATED
An earlier draft of this tool asserted "the decoder consumed the compressed
source EXACTLY" and that check FAILED: 0x3fd of 0x400 installed, 0x3fe of 0x400
vendor. The premise was wrong, not the decoder. The compressed length is stored
nowhere; it is DERIVED here as "region 1's source address to the end of SN_FWIN
record 1", and a record length is a multiple of four, so the stream is padded up
to a word boundary. The check now asserts what is actually true and is strictly
stronger than a loosened tolerance would be: the consumed length rounds up to
the derived length, AND every unconsumed byte is zero. Both hold in both
releases. The failing check was not deleted or relaxed; it was replaced with two
checks that test the real invariant.

Both went into ghidra/imports/. write_outputs() refuses any destination under
dumps/, uses exclusive create (open(path,"xb")), and refuses to overwrite an
existing file whose content differs. Re-running writes nothing. The output name
encodes source, destination, length and content hash, so it is self-describing
and deterministic: a second build produces byte-identical files.


STEP 4 — WHAT THE REGION ACTUALLY IS
This was not assumed from the region's role; it was read out of the decoded
bytes and cross-checked against evidence recorded long before this decode.

  +0x0008  05 01 09 06 a1 01 05 08 15 00 25 01 19 01 29 05 ...
           a HID REPORT DESCRIPTOR: Usage Page (Generic Desktop), Usage
           (Keyboard), Collection (Application), LED output page, and so on.
  +0x0284  05 0b 7e 1b 59 01
           consecutive little-endian halfwords idVendor=0x0b05,
           idProduct=0x1b7e, bcdDevice=0x0159 — the USB DEVICE DESCRIPTOR tail.
  +0x0850  "ASUSTeK"
  +0x0882  "ROG FALCHION ACE HFX"
  +0x08ec  "hid driver"
  +0x09a4  "Sonix HID"

notes/findings.md recorded `0b05:1b7e`, bcdDevice 1.59 from sysfs and lsusb in
the very first logs of this project, before any of this region was decoded. The
vendor image decodes to bcdDevice 0x0158 at the same offset, matching its own
filename M605_V01_00_58.bin. The decoder was never given a vendor ID, a product
ID or a version. Finding all three, adjacent and in device-descriptor order, in
the decoded output of both releases is EXTERNAL corroboration that the decode is
correct — not merely internally consistent.

So the region is the USB / HID DESCRIPTOR SET: initialised read-write data that
the scatter loader decompresses into RAM at boot, which is exactly what an ARM
__scatterload_decompress region is normally used for.

THE MEASUREMENT IS REPORTED AND IT DOES NOT SUPPORT ANY CONCLUSION. Thumb-2 is
a dense encoding: 0xb04 bytes of seeded pseudorandom noise decode at 95.53%,
known code decodes at 97.1-97.9%, and the reconstructed region decodes at
98.4-98.7% — ABOVE known code. A "98.7% Thumb-2 disassembly success rate" is
therefore not evidence that the region is code, and is not offered as such. The
control is why that is stated instead of the rate being quoted bare. What the
region is was settled in step 4, by its content.

The random control was imported as control_random_0xb04.bin and left in the
ignored project so the measurement can be reproduced. It is synthetic, is not
evidence, and no tool reads it.

STEP 7 — SEEDING: THREE ROOTS, ZERO NEW FUNCTIONS
Of the five loose candidates, three name addresses at which Ghidra ALREADY has
a function: 0x18018afc, 0x18018af0, 0x18018a28. They sit next to the "hid
driver" and "Sonix HID" strings, consistent with a driver structure holding
callbacks. The other two (0x1801e4ba, 0x1801e9d8) point inside the region
itself and are not functions; they are left alone.

That external agreement is the admission rule now written into
map_hardware_interfaces.py: a lone pointer from the region becomes a
reachability root ONLY when Ghidra independently recognises a function at the
address it names. No new function was created and no seeding run was needed —
the three targets were already in the inventory, so function counts are
unchanged at 101 (entry) and 573 (application) per release, and Phase 3 stays
valid without regeneration.

STEP 9 — PROVENANCE: TABLE 0x5680's MIDDLE ENTRY IS NOT A THIRD ROOT
Required record, so that one indirect root is not double-counted.

Table 0x5680 in the entry image has three entries at stride 24:
    0x00005680 -> 0x00004004
    0x00005698 -> 0x00004018
    0x000056b0 -> 0x000040b4
Log 104's seeding run reported `installed entry: created=3 existing=0 skipped=1`
and described the skip only as "already covered". The specific mechanism, read
out of the inventory for this log:

  - FalchionSeedVectors.java processes its arguments in the order given, which
    is ascending by address. It created PtrTarget_00004004 first.
  - Ghidra gave that function the body ranges 0x4004..0x4018 and 0x4019..0x401c
    (`hi` exclusive), i.e. an extent of 0x4004..0x401c with a one-byte hole.
  - createFunction(0x4018) then returned null, because 0x4018 lies inside the
    extent already claimed. That is the skipped=1.
  - 0x4018 is therefore NOT a function entry in installed_a.txt. It is absorbed
    into PtrTarget_00004004.

CONSEQUENCE: table 0x5680's three entries contribute TWO functions, not three.
reachability() previously dropped a root naming no function silently. It now
reports it, and the report line reads:
    roots naming no function: 0x00004018 (table@0x00005680)
so the arithmetic "3 entries -> 3 indirect roots" can no longer be written down
by accident. A unit test pins the behaviour, naming this case.


STEP 10 — WHAT IS STILL UNREACHED, AND WHY
No claim of full reachability is made. 427 of the application's 573 functions
are unreached. Split by whether anything in the image calls them:

  unreached                                427
    called by NOTHING in the image         135   <- each needs an entry mechanism
    called only by other unreached fns     292   <- downstream of those 135
    called by a REACHED function             0   <- would have been a traversal bug

The 135 callerless functions reach all 427 between them, so the gap is 135
missing entry points, not 427 separate mysteries. They total 13,457
instructions.

THE LARGEST UNACCOUNTED ENTRY MECHANISM, named precisely:
  - 0x1800023a, recorded in FINDINGS.md and logs 79-80 as Candidate B's runtime
    entry ("welcome to main"), IS NOT A FUNCTION IN THE INVENTORY AT ALL. It is
    absent from installed_b.txt, so it is neither reached nor unreached — the
    traversal cannot start there. This is the same contradiction
    map_hardware_interfaces.py already reports: no word in either release's
    Candidate A points at 0x1800023a, and the only cross-image code pointers are
    0x18016e69 and 0x18016f2d. Until that entry exists as a function, everything
    downstream of main is structurally unreachable.
  - 0x18001fbe, characterised in log 80 as the application's dispatcher, is the
    single largest callerless function at 3,146 instructions. Nothing in flash
    or in the reconstructed region points at it.
  - Log 80 also identified an RTOS with INIT_TASK and a scheduler. A task entry
    point handed to a task-creation call as a register argument is stored in no
    flash table and in no initialised data, so it is invisible to every survey
    run so far. This is a HYPOTHESIS about the remaining mechanism, stated as
    one; it has not been traced.

Flash-resident tables were already exhausted in log 104. The reconstructed
region is now exhausted too: it holds no table and its three usable pointers are
spent. The next mechanism to attack is argument-passed callbacks, which needs
data-flow, not a byte survey.

FAIL-CLOSED TESTS ADDED (tool/test_reconstruct_decompress.py, 23 tests)
Every failure path is asserted to FAIL. A decompressor that quietly returns
plausible bytes from a truncated or corrupted stream is worse than one that
refuses, because the wrong bytes would then be disassembled as if they were real.
  - a truncated stream raises; a stream ending mid-token raises
  - a back-reference before the start of output raises; one at the very first
    byte raises
  - a modified handler makes the tool refuse to decode at all
  - a one-byte flip in the real compressed stream must raise or produce
    different bytes; it may not be ignored
  - asking for the wrong length can overshoot it, which is why the produced
    length is checked against the descriptor rather than trusted
  - write_outputs refuses any path under dumps/, is exclusive-create, is
    idempotent for identical content, and refuses to overwrite different content
  - the format rules themselves: N-1 literals, zero-field indirection on both
    fields, field+2 back-reference length, overlapping repeat, zero fill
Two of these fixtures were hand-written wrong on the first run and corrected
against the decoder's behaviour after re-reading the handler; the decoder was
not changed.
