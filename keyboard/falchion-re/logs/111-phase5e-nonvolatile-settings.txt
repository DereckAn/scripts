STEP 1 — THE COMMIT BRANCH CONTAINS NO CALL
================================================================================
The dispatcher's opcode test, from its listing:

    18002014  cmp r2,#0x43
    18002018  cmp r2,#0x50
    1800201a  beq 0x18002110          <- the 0x50 branch
    1800201c  cmp r2,#0x51
    18002020  b   0x1800248e          <- the 0x51 configuration handlers

and inside the 0x50 branch, the subcommand test:

    180023de  ldrb r0,[r4,#0x1]       ; request byte 1
    180023e0  cmp  r0,#0x55
    180023e2  beq  0x18002428         <- THE COMMIT
    180023e6  cmp  r0,#0x30
    180023ea  cmp  r0,#0x40
    180023f0  cmp  r0,#0x60

The commit target, in full — nine instructions, and NOT ONE OF THEM IS A CALL:

    18002428  ldr    r0,[0x180025a0]  ; *(0x180025a0) = 0x18022c60
    1800242a  adds   r0,#0x84
    1800242c  ldrb   r1,[r0,#0x0]
    1800242e  cmp    r1,#0x4
    18002430  beq    0x18002508       ; already 4 -> skip; the commit is idempotent
    18002432  strb.w r12,[r0,#0x0]    ; r12 = 4, from `mov.w r12,#0x4` at 0x18001fea
    18002436  strb   r5,[r0,#0x8]     ; a sub-selector
    18002438  ldrb   r1,[r0,#0x9]
    1800243a  bic    r1,r1,#0xc       ; clear two flag bits
    1800243e  b      0x18002420

For contrast, the neighbouring 0x60 subcommand at 0x18002440 DOES call
(`bl 0x1800072c`, `bl 0x18000584`), so the absence of a call at 0x18002428 is a
property of this branch and not of the disassembly.

ANSWER TO THE PHASE'S FIRST QUESTION: (b) THE COMMIT QUEUES WORK. It sets a
command byte at 0x18022ce4 to 4 and returns. Not (a): it programs nothing. Not
(c): it invokes no ROM and no other core. Not (d): there is no table dispatch
here.

So the transfer is DMA-driven, bounds-checked on its SOURCE, and gated on a
per-channel busy bit.

WHAT IS *NOT* ESTABLISHED, and this is the important part. The opcodes 0xd8 and
0x52 are the JEDEC SPI-NOR block-erase opcodes for 64 KiB and 32 KiB. THAT IS
RECOGNITION, NOT PROOF. What the code demonstrably does is place those bytes in
a struct that a DMA path consumes. No SPI controller register was identified.
0x40020000 and 0x45000000 are NOT NAMED here — naming them from an opcode I
recognised would be exactly the correlation this project refuses.

THE STORAGE MEDIUM IS THEREFORE RECORDED AS UNIDENTIFIED. Internal MCU storage,
external U5 SPI NOR and a RAM mirror all remain consistent with the evidence.
The path is also NOT the bootloader's flash controller from log 81: that path
programs 0x10000..0x7c000 through its own primitives, and nothing here touches
them.

ON THE 0x51/0x22 WRITE PATH THAT LOG 110 LEFT UNTRACED: the 0x51 branch begins

that gap is recorded rather than assumed closed. What IS closed is the second
half: RAM state -> command byte -> erase, which is this log's subject.

The dirty-flag behaviour FINDINGS describes for the 0x51 handlers is consistent
with a two-stage design — 0x51 mutates RAM, 0x50/0x55 requests persistence —
and the absence of any erase call under 0x51 supports it. Recorded as
consistent, not as proven.

================================================================================
STEP 7 — THE EXIT GATE: WHICH BRANCH THE EVIDENCE SUPPORTS
================================================================================
The gate is dual: document the format and write call graph well enough EITHER to
implement safe persistence OR to deliberately omit all writes while proving a
prototype cannot corrupt existing configuration.

THE EVIDENCE SUPPORTS THE SECOND BRANCH ONLY.

Safe persistence CANNOT be implemented from this evidence: the format's magic,
version, length and checksum were not recovered, the storage medium is
unidentified, and the source of the persisted data was never found. Writing
under those conditions would be guesswork against a medium this project has not
identified.

The negative CAN be proven, and the argument is short:
  1. The only routes into an erase are FUN_1800e2a8 and FUN_1800e2c4.
  2. Both are called only from FUN_18000d56's sub-switch, which runs only when
     the command byte at 0x18022ce4 is non-idle.
  3. Within the traced set, the only writer of that byte is the dispatcher's
     0x50 branch.
  4. Both primitives additionally refuse unless byte 0 of the request struct at
     0x18025ef4 is zero, and they are the only writers of the opcode field.
  Therefore a firmware that never writes 0x18022ce4, never fills 0x18025ef4,
  never calls those two functions and never dispatches 0x50/0x55 cannot reach
  an erase.

WHAT A CUSTOM FIRMWARE MUST PROVABLY NEVER DO:
  - write 0x18022ce4
  - write the request struct at 0x18025ef4
  - call FUN_1800e2a8 or FUN_1800e2c4, or their vendor counterparts
  - dispatch vendor opcode 0x50 subcommand 0x55

THE RESIDUAL, stated because the proof is only as good as its scope: steps 2-4
of that argument hold WITHIN THE TRACED SET. FUN_18000d56 and FUN_1800dc92 are
both callerless in the application call graph, so the context that runs them is
not established, and this log does not exclude a second writer of the command
byte outside the traced set. The proof is therefore conditional on the traced
set being complete, and that condition is NOT proven.
