STEP 2 — WHAT DRIVES IT: THE SERVICE TASK IS A BUSY-SPIN EVENT PUMP
================================================================================
FUN_180061c2's only in-image caller is FUN_18008c16, which log 106 recorded as
callerless. A value cross-reference for 0x18008c16 and 0x18008c17 over the
application, and an aligned-word search over the entry image, the region and the
application, return NOTHING — the address is stored nowhere. The chain is
entered from outside the application image.

Log 106 recovered Task_OEM_MAIN_SERVICE_TASK at entry-image 0x498, created by
INIT_TASK with a 16 KiB stack at priority 10 — sixteen times any other task's
stack. Decompiled read-only:

    00000498  push {r1,r2,r3,lr}
    0000049a  ldr  r4,[0x000005b0]
    000004b2  ldr  r0,[r4,#0x0]
    000004b4  cmp  r0,#0x0
    000004b6  beq  0x000004b2          <- BUSY-SPIN on the event word
    000004a0  cpsid i                  <- mask interrupts
    000004a2  ldr  r0,[r4,#0x0]
    000004a6  str  r5,[r4,#0x0]        <- read-and-CLEAR
    000004a8  cpsie i                  <- unmask
    000004ac  cbz  r0,0x000004b2
    000004ae  bl   0x0000042c

  *(0x5b0) = 0x1801ee84

THE SYNCHRONISATION DISCIPLINE IS INTERRUPT MASKING. The read and the store are
bracketed by cpsid i / cpsie i, so a tick arriving between them cannot be lost.
The task NEVER blocks on a queue or a semaphore — it spins. That is a real
scheduling fact and it is why this task holds the largest stack and a high
priority.

0x1801ee84 is exactly where Phase 3 placed the start of the zeroinit region.

-0x1f — the modifier and international key ranges), and advances a three-deep
ring at *(base+0x14). It consumes key state; it does not acquire it.

STEP 7 — WHERE THE PIPELINE BOTTOMS OUT
================================================================================
FUN_180061c2 reads two shared objects:

  0x1801e734  = region+0x3b4, the key-state struct. Twelve functions across the
                0x18004xxx-0x18006xxx report range load it from a literal pool.
                Fields used: +0xc (element count), +0x28/+0x50 (a change flag
                pair), +8, +6.
  0x18023410  = zeroinit RAM. FUN_180061c2 clears it with
                  memset(0x18023410 + 0x14, *(0x1801e734+0xc) << 1)
                The SHIFT BY ONE makes the elements two bytes wide. A per-key
                HALFWORD array is what a Hall-effect keyboard's analog readings
                would live in; a contact matrix would not need 16 bits per key.

A value cross-reference for both addresses returns twelve functions, ALL inside
the 0x18004xxx-0x18006xxx report and policy range. FUN_18005a88 — which
FUN_180061c2 calls first — is the heaviest user of the halfword array with eight
literal loads.

NO FUNCTION IN THE RECOVERED CHAIN WRITES THAT ARRAY FROM A HARDWARE REGISTER.

THE FINDING, stated as the prompt requires rather than forced into a
contact-matrix model: the scan pipeline as recovered runs from IRQ38 through the
service task and the prescaler into report assembly over a per-key 16-bit array,
and it bottoms out at that array. The producer is not recovered. The device is
Hall-effect, the array is 16 bits per element, and the detailed acquisition
arithmetic is 5D's subject. No row, column, drive or settle behaviour is
asserted, because none was observed.

STEP 8 — PHYSICAL DIMENSIONS: WHAT IS PROVEN AND WHAT IS NOT
================================================================================
THE 189-ENTRY TRANSLATION TABLE IS NOT USED AS A KEY COUNT ANYWHERE in this
phase's tooling, and a unit test asserts the string "189" appears in no
dimension field of the emitted model.

PROVEN, each read out of a report descriptor's own HID items:
  interface 3 (NKRO): Report Size 1 x Report Count 0x98 = 152 bits = 19 bytes,
      Usage Minimum 0x00, Usage Maximum 0x98. 152/8 = 19 is exactly the packet
      size the host enumerated. This is a REPORT dimension — the number of HID
      usage codes the bitmap covers — and it is not a key count.
  interface 0 (boot): an 8-byte packet, the standard 1 modifier + 1 reserved +
      6 key slots.
  Both releases produce identical dimensions for all five interfaces.

NOT PROVEN — rows, columns, key count. The per-key array's element count is
*(0x1801e734+0xc), a RUNTIME value: the region's initialised image has that
field zero (region+0x3c0 = 00 00 00 00), so no static constant fixes it. No loop
bound or mask width in the recovered chain fixes it either. Recorded as
unresolved with that reason, in the emitted JSON and in the report.

WHAT CAN PRE-EMPT OR BLOCK A SCAN, from the recovered structure:
  - the service task busy-spins rather than blocking, so it is always runnable;
    at priority 10 any higher-priority task (INIT_TASK at the clamped 14) can
    pre-empt it, and it will consume the remainder of its slice otherwise.
  - IRQ38's write and the task's read-and-clear cannot interleave destructively,
    because the task masks interrupts across the pair.
  - a tick raised while the task is inside FUN_0000042c is NOT lost: the flag is
    a level, set to 1, and the next spin iteration observes it. But two ticks
    arriving before one drain are INDISTINGUISHABLE from one — the flag is a
    single word set to 1, not a counter. The separate 16-bit counter at
    region+0 is incremented by the ISR and is not consulted by the drain loop.
    THAT IS A REAL PROPERTY of the design and it is recorded, not judged.
  - the USB transmit can fail three ways (log 107); FUN_18004164 maps any of
    them to a return of 2, and FUN_180061c2's call sites do not branch on it.

CADENCE CLAIMS ARE LABELLED. Source: OBSERVED (IRQ38 is the sole writer).
Divider ratios: OBSERVED (compare constants in the listing). Absolute period:
UNRESOLVED — the timer that raises IRQ38 is not identified and nothing here
observed a clock. Call-graph reachability is not timing.
