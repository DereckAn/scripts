WHY 5A COMES FIRST
Ghidra's call graph cannot follow a call made through a pointer held in a
table, so before this subphase only 51 of the application's 530 functions
were reachable from any evidence-backed root. Every later subphase — USB,
scan, Hall/ADC, settings, RGB — inherits that blindness, because a function
with no context cannot be placed in a task or an interrupt. 5A therefore
recovers the tables first.

STEP 1 — THE DETECTION RULE
A candidate is a word with the Thumb bit set whose target, once that bit is
cleared, is an even address at or above the image's first code address. A
lone such word proves nothing, so a candidate is reported only as part of a
run of at least three at a constant stride. The code floor matters: without
it, structure words that happen to carry bit 0 produce targets like
0x00000004, and the first cut of this tool reported exactly that.
$ python3 tool/find_pointer_tables.py | sed -n '1,6p'
  PROGRAM find_pointer_tables
  PURPOSE locate function-pointer tables so their targets can be seeded
  RULE a run of at least 3 Thumb pointers at a constant stride from (4, 8, 12, 16, 20, 24, 32), each targeting an even address at or above the image's first code address. A lone word that looks like a pointer is not reported as a table.

  IMAGE entry base=0x00000000 size=0x58ac code_floor=0x140
    slice=installed_app_a_slot0_flash11000_dst00000000_len058ac_f093979a.bin
  [exit 0]

STEP 6 — WHAT 5A DID NOT CLOSE
435 of the application's 573 functions are still unreached. Flash-resident
tables are now exhausted: the detector finds no further run of three, and
the nine remaining loose candidates are single words that the stated rule
declines to call a table.

  24
  [exit 0]
  NOTE loose candidates across both images; each is a single word, not a run

So the remaining entry mechanisms are outside flash tables. The three
possibilities, none yet distinguished:
  * a callback installed into RAM at runtime, which no static table shows;
  * a table inside the decompressed region 0x1801e380..0x1801ee84, which
    Phase 3 mapped but did not reconstruct because the ARM decompressor
    was not reimplemented;
  * dispatch through a computed value rather than a stored pointer.
The second is testable offline and is the concrete next step: reconstruct
the decompressed region and re-run this detector over it.

STEP 7 — THE SERIES-LEVEL SOURCE, AND WHAT IT MAY NOT DO
The SNC7320-series product brief was added as a reference at the owner's
direction. It is series-level and carries no SNC73270 register map, so no
register identity in this repository is assigned from it. It was NOT
fetched: the URL and its summary were supplied by the owner, so every
log's 'no network access' assertion stays true.
$ sed -n '/^### What it may not be used for/,/^### Where it is used/p' notes/references.md
  ### What it may not be used for

  It is a **product brief for the SNC7320 series**, not a register map for the
  SNC73270. It carries no register addresses, no bit fields and no interrupt
  assignment table.

  **Therefore no register identity in this repository may be assigned from it
  alone.** It can raise or lower the prior on a hypothesis — for example, "two
  identical magic-key-protected blocks on the reset path" is consistent with the
  brief's *two watchdogs*, and a six-channel SAR ADC is consistent with a
  Hall-effect front end — but a consistency is not an identification. Any claim
  that a given address is a given peripheral still needs data-flow evidence from
  the image, and must carry its own confidence level.
