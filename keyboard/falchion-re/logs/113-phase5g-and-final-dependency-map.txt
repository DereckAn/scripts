STEP 2 — WATCHDOGS
================================================================================
$ a per-function MMIO census over BOTH peripheral maps, filtered to the two
$ magic-key blocks

  app:   functions touching 0x40008000 / 0x40009000: NONE
  entry: functions touching them: 0x00001216 (FUN_00001216)

EXACTLY ONE FUNCTION IN EITHER IMAGE TOUCHES THEM, and it is on the reset path.
It writes the key 0x5afa55aa to +0xc and then 0x5afa0000 to +0 of both blocks.
NOTHING RE-ENABLES OR FEEDS THEM ANYWHERE.

The control value's low half is ZERO, which is what a disable looks like. But
no register map confirms the bit meanings, so this is INFERENCE FROM THE WRITE
PATTERN, NOT IDENTIFICATION, and the model records it as strongly-inferred.
The series brief's "two watchdogs" and the two identical blocks are a
consistency hint, and a periodic magic write would be a lead rather than proof —
but there is no periodic write here at all, which is a stronger fact than
either.

THE usbd_wdt LEAD DOES NOT PAN OUT. The prompt flagged the task name as a lead
rather than evidence, and tracing it settles the matter:

  usbd_wdt task body FUN_18015c84: insns=37 callees=4 reach=12
    MMIO in closure: ['0xe000ed04']
    touches a watchdog block: False

Its entire twelve-function closure reaches only ICSR, the RTOS yield. It is a
USB-device software supervisor, not a hardware watchdog feeder. Had the name
been taken as evidence, this phase would have concluded the opposite.

SAFE REPLACEMENT POLICY: perform the same disable. A replacement that simply
ignores the blocks inherits whatever their reset default is, and that default
is not established anywhere. So the watchdogs are MUST-NEUTRALIZE, not may-omit.

STEP 4 — MULTICORE: THE START MECHANISM IS FOUND
================================================================================
Log 104 left this as the open question: the RAM image at flash 0x74000 ->
0x18038000 has its own vector table and reset vector, and nothing was found
that starts it. It is found now.

An aligned-word search for the descriptor values across every preserved image:

  entry+0x2000 (0x00002000) holds 0x60074000     <- the flash source
  entry+0x2004 (0x00002004) holds 0x18038000     <- the RAM destination
  app+0x3f0   (0x180003f0) holds 0x60074000
  ram18038000+0x4 (0x18038004) holds 0x180381c1  <- its own reset vector

The entry-image pair at 0x2000/0x2004 has NO loader — nothing reads it. The
application's copy does. CandidateB_Main's opening listing:

    1800023a  push {r2,r3,r4,lr}
    1800023c  mov.w r4,#0x20000000
    18000240  movs r5,#0x0
    18000242  ldr r0,[0x180003f0]      ; r0 = 0x60074000
    18000244  str r5,[r4,#0x0]         ; *(0x20000000) = 0
    18000246  bl 0x1801bd96            ; a cross-image veneer
    1800024a  ldr r0,[0x180003f4]      ; r0 = 0x12345678
    1800024c  ldr r1,[r4,#0x0]
    1800024e  cmp r1,r0
    18000250  bne 0x1800024c           ; SPIN until the mailbox holds the token
    18000252  str r5,[r4,#0x0]         ; then clear it

  *(0x180003f0) = 0x60074000   *(0x180003f4) = 0x12345678

WHERE DOES THE TOKEN COME FROM? An exhaustive aligned-word search of the entry
slice, the application slice, the reconstructed region, the bootloader mirror
and the 0x18038000 RAM image:

  entry:        0x12345678 at NOWHERE
  app:          0x12345678 at ['0x3f4']          <- the expected value
  region:       0x12345678 at NOWHERE
  boot:         0x12345678 at NOWHERE
  ram18038000:  0x12345678 at ['0x3214']         <- INSIDE THE SECOND IMAGE

The token the application waits for exists in exactly two places, and one of
them is inside the image at 0x18038000. That is the evidence log 104 lacked.

THE START ROUTINE. The veneer at 0x1801bd96 is `41 f6 51 7c c0 f2 00 0c`,
which decodes as `movw r12,#0x1f51` / `movt r12,#0x0` — entry-image 0x1f50.
Ghidra had not disassembled it because it is unreached, so it was validated
directly:

  TARGET addr=0x1f50 thumb=true mapped=true valid_subroutine=true decoded=8
         prologue=push_{r4,r5,r6,lr} defined=false at=none
  raw bytes: 70 b5 40 07 02 d0 4f f0 ff 30 70 bd 4f f0 8a 44 28 4d d4 f8 00 01
             4f f4 00 42 20 f4 00 40 c4 f8

It is a real function: a standard prologue, eight instructions decoding
cleanly, and a read-modify-write of [r4,#0x100] clearing bit 15 — and the entry
image's census records 0x45000100 and 0x4500010c in that same block. So THE
START MANIPULATES 0x45000100. The block is NOT named.

SO THE MECHANISM IS: main hands the flash address 0x60074000 to entry-image
0x1f50 through a veneer; that routine manipulates 0x45000100; main then spins
until 0x20000000 holds 0x12345678, a token that lives inside the started image.
A second execution context with a mailbox handshake.

WHAT IS STILL UNRESOLVED, and it matters: WHAT THE SECOND CONTEXT OWNS. No
evidence assigns USB, the Hall acquisition or storage to it. It is a strong
CANDIDATE owner of the Phase 5D acquisition boundary — precisely because that
producer was never found in either analysed image — but a candidate is not a
finding, and the model records it as unresolved. A unit test enforces that it
is not promoted.

NO ROM SERVICE WAS IDENTIFIED. Every cross-image call recovered so far resolves
into one of the preserved images. A mask ROM was not searched and cannot be, so
its absence is unproven either way and is recorded as a platform dependency
boundary rather than as an absence.

THE GATE HAS TEETH, AND THE CHECKS ARE THE TEETH. Three of them exist purely to
make "five unanalysed service areas plus an MMIO census" impossible to pass off
as completion:
  - every UNRESOLVED service must name an evidence boundary of more than 60
    characters; a bare "unknown" fails the run
  - no service may be MAY-OMIT without a proven safe idle state
  - the contrapositive: any service whose idle state is unproven must NOT be
    may-omit. RGB is the case that rule exists for, and it is why RGB is a
    blocker here even though its protocol is fully recovered.
A fourth check requires every class to be non-empty, so the classification is a
real partition rather than a pile in one bucket.

NO RESET-REACHABLE WRITE IS CALLED AN INITIALISATION REQUIREMENT SOLELY BECAUSE
OF GRAPH REACHABILITY. Each must-implement service names a consumer that fails
without it: no tick means no key state, no control endpoint means no
enumeration, no stack window means the reset path faults out. The blocks the
init chain writes are preserved as a SEQUENCE, not asserted as requirements.

THAT IS A HYPOTHESIS, NOT A FINDING. Testing it would mean analysing the
0x18038000 image itself, which is preserved in ghidra/imports and has not been
imported or analysed in project-step6.
