Log 94's parse_records stopped at the first slot whose address or length was
zero. Three consequences, all reproduced by the reviewer:
  * a nonzero-length record whose address is zero was ignored;
  * an active record after a zero-length hole was ignored, so its checksum
    dependency would have been invisible to the Phase-2 comparator and the
    Phase-7 builder;
  * a fully populated eight-slot table was rejected as unterminated.

The reviewer's own reproduction: an in-memory image with an active slot 3
behind the empty slot 2, with the application word-sum corrected, returned
known_checks_ok=True while omitting slot 3. Reproduced and re-run after the fix:

FIX
tool/falchion_image.py parse_records now mirrors FUN_0000511c:
  * it scans exactly MAX_RECORDS = 8 slots;
  * it skips a slot only when the length field is zero;
  * it continues past holes and preserves physical slot indices;
  * it bounds-checks every active slot against the image;
  * a zero address with a nonzero length raises ImageFormatError naming the
    slot, instead of being read as a terminator;
  * a table truncated before all eight slots raises ImageFormatError;
  * an all-zero-length table raises ImageFormatError.
The 'unterminated table' concept and its test are removed. Slot 2 of both
preserved images carries address 0x60021000 with length 0, so the old rule
happened to stop for the right number of records by the wrong reason.
