THE FIRST REAL FINDING IS A NEGATIVE ONE. **EVERY ONE OF THE THIRTEEN MAIN
ITEMS IS A FEATURE ITEM. THERE IS NO OUTPUT REPORT.** Interface 4 has a 64-byte
OUT endpoint 0x0f and declares nothing to send over it. So the LampArray
protocol runs over CONTROL transfers, and Phase 5B's "EP 0x0f -> class ops ->
lighting consumer" framing pointed at the wrong endpoint. The consumer is real;
it is just not on EP 0x0f.

SPEC-DERIVED NAMES, labelled as such. Usage page 0x59's report semantics are
fixed by the LampArray specification, not observed here:
  ID 1 LampArrayAttributes    ID 4 LampMultiUpdate
  ID 2 LampAttributesRequest  ID 5 LampRangeUpdate
  ID 3 LampAttributesResponse ID 6 LampArrayControl
Every SIZE above is measured from the descriptor. Only the NAMES are spec-derived.

STEP 2 — THE ROUTE FROM THE CONTROL ENDPOINT
================================================================================
FUN_180184b6 is the class-ops control handler. Its request codes, decompiled:

    if (uVar10 == 0x8106)  ... GET_DESCRIPTOR, types 0x21 and 0x22
    if (uVar10 == 0x2109)  ... SET_REPORT
    if (uVar10 == 0xa101)  ... GET_REPORT
    0x210a SET_IDLE, 0x210b SET_PROTOCOL, 0xa102 GET_IDLE, 0xa103 GET_PROTOCOL

and `uVar2 = param_2[1] >> 8` is the report TYPE. For type 3 (Feature) BOTH
directions converge on one indirect call:

    GET: (*(code *)*piVar3)(uVar15, *(byte *)((int)param_2 + 1), *puVar13, &local_2c)
    SET: if (0x3f < uVar14) return -0x5f;      <- a 64-byte cap
         (*(code *)*piVar3)(...)

with piVar3 = DAT_18018860 = 0x1801ebb8, the USB core struct. Its first word is
the Feature callback. Phase 5B's cross-reference had already recorded the one
writer of that word:

    REF value=0x1801ebb8 from=18018bb4 in=FUN_18008f4a type=WRITE

FUN_18008f4a is five instructions and settles it:

    18008f4a  adr.w r0,0x18008f13
    18008f4e  b.w   0x18018bb2
    18018bb2  ldr   r1,[0x18018cd0]     ; 0x1801ebb8
    18018bb4  str   r0,[r1,#0x0]
    18018bb6  bx    lr

Log 106 recorded INIT_TASK's first call as FUN_18008f4a, so the callback is
installed at startup. THE FEATURE CALLBACK IS 0x18008f12.

    18008f16  cmp r1,#0x1  -> FUN_1800ffaa   ; bRequest 1  = GET_REPORT
    18008f1a  cmp r1,#0x9  -> FUN_18010102   ; bRequest 9  = SET_REPORT
    18008f1e  cmp r1,#0xff -> a debug print
    18008f22  mvn r0,#0x15                   ; anything else -> -0x16

A NOTE ON A MISREADING I MADE AND CORRECTED. On first pass I read
FUN_18008f12's param_1 as the interface number and concluded interface 4 was
unhandled. The call site settles it: uVar15 = `param_2[1] & 0xff` is wValue's
low byte, the REPORT ID, and byte 1 of the setup packet is bRequest. The
handler dispatches on bRequest and passes the report ID down. Reading the call
site rather than the callee's decompiled signature is what fixed it.

LAMP ADDRESSING IS BY LampId THROUGH A COORDINATE TABLE. Each LampId indexes a

FUN_1800c132. Every LampId is bounds-checked against the active
configuration's lamp count first.

STEP 4 — THE FRAME BUFFER, FROM THE LISTING
================================================================================
FUN_1800c132(row, column, channels), complete:

    1800c132  push {r4,lr}
    1800c134  cmp r0,#0x6
    1800c136  bcs 0x1800c16c            ; row  >= 6  -> drop
    1800c138  cmp r1,#0x11
    1800c13a  bcs 0x1800c16c            ; col  >= 17 -> drop
    1800c13c  ldrb r3,[r2,#0x0]         ; red
    1800c13e  ldrb r4,[r2,#0x3]         ; intensity
    1800c140  add.w r0,r0,r0, lsl #0x4  ; row * 17
    1800c144  muls r3,r4
    1800c146  add.w r4,r0,r0, lsl #0x1  ; * 3
    1800c14a  ldr  r0,[0x1800c428]      ; frame base
    1800c14c  add.w r1,r1,r1, lsl #0x1  ; col * 3
    1800c150  add  r0,r4
    1800c152  lsrs r3,r3,#0x8           ; (red * intensity) >> 8
    1800c154  strb r3,[r0,r1]           ; cell + 0
    1800c156  ldrb r3,[r2,#0x1]         ; green
    ...       strb r3,[r0,#0x1]         ; cell + 1
    1800c162  ldrb r1,[r2,#0x2]         ; blue
    ...       strb r1,[r0,#0x2]         ; cell + 2
    1800c16c  pop {r4,pc}

  FRAME BUFFER  *(0x1800c428) = 0x1802505e, in the zeroinit region
  GEOMETRY      6 rows x 17 columns x 3 bytes = 306 bytes, 102 cells
  ORDER         red, green, blue at cell offsets 0, 1, 2
  WIDTH         8 bits per channel
  INTENSITY     (channel * intensity) >> 8, applied per channel
  BOUNDS        row < 6 and column < 17, otherwise DROPPED SILENTLY — both
                `bcs` branches jump straight to the return

LED COUNT FROM EVIDENCE, NOT MARKETING. The lamp count is read from a table the
handler indexes as `*(byte *)(DAT_18010140 + kind*8)`, and DAT_18010140 =
0x0000500c — an address in the ENTRY IMAGE, not the application. Read from the
entry slice's raw bytes:

    record 0: 54 1b 7b d1 2e df 04 01   count = 84
    record 1: 55 1b 7b d1 2e df 04 01   count = 85
    record 2: 59 1b 7b d1 2e df 04 01   count = 89
    record 3: 17 10 32 04 73 01 02 00   count = 23
    record 4: 25 16 32 04 73 01 02 00   count = 37
    record 5: 33 1c 32 04 73 01 02 00   count = 51
    record 6: 41 22 32 04 73 01 02 00   count = 65
    record 7: 4f 28 32 04 73 01 04 00   count = 79

Eight configuration variants, 23 to 89 lamps, EVERY ONE OF THEM <= the frame's
102 cells. That consistency is a check, not a coincidence, and the tool asserts
it. TOPOLOGY: the frame is a 6 x 17 grid and lamps are placed into it by a
coordinate table, so the addressing is a MATRIX. Whether the physical wiring is
a matrix, a chain or something else is NOT established — the grid is a software
layout.

================================================================================
STEP 6 — THE SAFE-OMISSION QUESTION
================================================================================
Answered in two halves, because only one of them is provable.

PROVABLE — THE BUFFER'S IDLE STATE. The frame lives at 0x1802505e, inside the
zeroinit region Phase 3 recovered, so it powers up ALL ZERO. Only FUN_1800c132
ever writes it (the cross-reference above is exhaustive). A firmware that omits
RGB and never calls that function therefore leaves an all-zero frame, by
construction and not by convention.

NOT PROVABLE — WHETHER ALL-ZERO MEANS THE LEDS ARE OFF. That depends on the
driver's polarity, and the driver is unidentified. A common-anode part driven by
an inverting stage would read all-zero as FULL BRIGHTNESS. Nothing in the
recovered code settles it.

ALSO NOT ESTABLISHED: whether any clock, pin or controller the lighting path
initialises is SHARED with a mandatory service. The initialisation is in the
unreached consumers, so it could not be inspected. A first custom firmware that
omits RGB must therefore treat this as an open risk rather than a solved one.


================================================================================
STEP 7 — CLASSIFICATION
================================================================================
The exit gate asks for RGB to be classified as implemented or safely omitted.

CLASSIFICATION: **IMPLEMENTED**, with a stated ceiling. All six LampArray
reports are handled, lamps are addressed by LampId through a coordinate table,
bounds are checked, and a 306-byte frame is written with intensity-scaled RGB —
enough to reproduce the HOST-FACING protocol exactly. What is missing is the
final hardware interface, so a replacement firmware built from this evidence
could satisfy a LampArray host and still light nothing.

SAFE OMISSION IS NOT YET JUSTIFIED, for the reason in step 6: the buffer's idle
state is provable and the hardware's is not.
