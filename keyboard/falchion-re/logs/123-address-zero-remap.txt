THE ANSWER: THERE IS NO REMAP. Address 0 is ordinary writable RAM by hardware
arrangement, and no preserved image configures, enables or relocates anything
to make that true. The question was framed as "find the remap control"; the
correct answer is that there is not one to find.

A CORRECTION TO THE PROMPT'S PREMISE, FIRST. The prompt states that the series
brief "documents ROM/RAM remapping as a series feature". IT DOES NOT.
notes/references.md lists dual Cortex-M3 cores, USB host and device, GPIO,
timers and PWM, two watchdogs, an SPI NOR interface and a 10-bit six-channel
SAR ADC. The word "remap" does not appear in the file at all. The lead does not
exist in this repository, and nothing below rests on it — which is just as
well, because the evidence says there is no remap to find.

================================================================================
STEP 2 — THE HANDOFF STUB, IN FULL
================================================================================
FUN_00007ec8 does not copy to address 0 itself. It calls a veneer:

    00007f1a  movs r0,#0x0             ; dst = 0
    00007f1c  bl 0x00000ffc            ; -> a bare `bx lr`. A NO-OP STUB.
    00007f20  mov r0,r4                ; the selected entry
    00007f22  bl 0x00007fa8            ; the slot-7 setter, below
    00007f26  mov.w r2,#0x10000        ; length
    00007f2a  mov r1,r4                ; src
    00007f2c  movs r0,#0x0             ; dst
    00007f2e  bl 0x00000fee            ; movw/movt r12,#0x18010001 ; bx r12

  0x00000ffc IS A BARE `bx lr`. Whatever hook that slot exists for — a cache
  operation, a remap, a platform quirk — THIS SOC NEEDS NOTHING THERE.

  0x00000fee is a veneer into RAM at 0x18010000, which is the preserved 0x50-
  byte boot-handoff image. The copy must run from RAM because it overwrites
  address 0, where the bootloader is executing.

THE STUB, ALL 0x50 BYTES:

    18010000  mov r3,r0                ; dst
    18010004  mov r6,r1                ; src
    18010006  movs r4,#0x1
    18010008  msr primask,r4           ; DISABLE INTERRUPTS
    1801000e  lsrs r2,r2,#0x2          ; length -> word count
    18010014  ldr.w r4,[r6,r0,lsl #0x2]
    18010018  str.w r4,[r5,r0,lsl #0x2]  ; WORD COPY INTO ADDRESS 0
    1801001e  cmp r0,r2 / bcc 0x18010014
    18010024  dsb #0xf
    18010028  ldr r4,[0x18010048]      ; = 0xe000ed0c, AIRCR
    1801002a  ldr r4,[r4,#0x0]
    1801002c  and r4,r4,#0x700         ; preserve PRIGROUP
    18010030  ldr r7,[0x1801004c]      ; = 0x05fa0000, VECTKEY
    18010032  orrs r4,r7
    18010034  adds r4,r4,#0x4          ; | SYSRESETREQ
    18010038  str r4,[r7,#0x0]         ; SYSTEM RESET
    1801003a  dsb #0xf
    18010044  b 0x18010042             ; spin until the reset lands

  Its ONLY two literals are 0xe000ed0c and 0x05fa0000, both ARMv7-M
  architectural. IT WRITES NO SYSTEM-CONTROL REGISTER. It masks interrupts,
  copies, and resets. Address 0 is ALREADY WRITABLE when it runs.

THE HANDOFF VARIABLE, and it is quietly good evidence:

    00007fa8  ldr r1,[0x00007fb0]      ; = 0xe000ed08, VTOR
    00007faa  ldr r1,[r1,#0x0]         ; the table's base
    00007fac  str r0,[r1,#0x1c]        ; slot 7 = the selected entry
    00007fae  bx lr

  Vector slot 7 is ARMv7-M's Reserved7, and BOTH images ship it as 0x00000000,
  so it is scratch. The bootloader parks the selected entry address there
  immediately before the copy and the reset. THAT THE WRITE WORKS AT ALL MEANS
  THE VECTOR TABLE IS IN WRITABLE RAM — which is the same conclusion the copy
  gives, reached independently.

WHAT ADDRESS 0 IS, AT EACH STAGE:

  ROM or hardware boot   the bootloader, somehow    UNRESOLVED — see step 4
  bootloader running     the bootloader (table at 0, reset 0x000002f5)
  handoff                being overwritten, by the RAM stub
  after the reset        the entry image (table at 0, reset 0x000014a9)
  application running    STILL the entry image — the app is copied to
                         0x18000000 and its handlers are entered through the
                         table at 0

  WHAT MAINTAINS IT AFTER THE APP STARTS: nothing, because nothing established
  it. There is no VTOR write and no remap write anywhere. The arrangement is
  static.

IT IS NOT AN ALIAS OF 0x18000000, and this one is an inference rather than an
observation, so it is labelled strongly-inferred. If address 0 aliased
0x18000000, then the entry image's own scatter loader at 0x148 — which copies
0x1e354 bytes from flash to 0x18000000 — would be copying over itself while
executing from itself, and would be destroyed mid-copy. It is not. Corroborating
this, both stages run code at 0 while placing their STACK in the 0x18000000
window: the bootloader's initial SP is 0x1802b230 and the entry image's is
0x18036168, and the entry image's own init bounds-checks MSP into
[0x18000000, ...] and faults otherwise. The code window and the data window are
distinct memories.


================================================================================
STEP 3 — WHAT A REPLACEMENT MUST REPRODUCE
================================================================================
Six things, every constant read from bytes, and the last one is the point:

  1. SIT WHERE THE BOOTLOADER LOOKS. It compares the selected entry against
     0x60011000, read from its own pool at 0x00007f98, and refuses anything
     else.
  2. FIT THE FIXED COPY. The length is a hard-coded 0x10000 and is not
     negotiable; the source must be readable for the whole 0x10000. The vendor
     entry image is 0x58ac, so there is room.
  3. PUT THE VECTOR TABLE AT IMAGE OFFSET 0. The image lands at address 0 and
     VTOR is never written, so the table must be the first thing in it.
  4. PUT THE STACK IN THE 0x18000000 WINDOW. Both preserved stages do, and the
     entry image's init faults if MSP is outside it.
  5. CONFIGURE NO REMAP, AND NEVER WRITE VTOR. Nothing in any preserved image
     does either.
  6. DO NOT ASSUME VECTOR SLOT 7 IS ZERO AT RUNTIME. The bootloader writes the
     selected entry there before the reset. A replacement may read it or ignore
     it; it must not rely on it being clear.

  PRESERVING THE ARRANGEMENT MEANS LEAVING IT ALONE. That is the easiest
  obligation this project has produced, and it is a genuine result: the gate
  asked which register arrangement a replacement must preserve, and the answer
  is none.


================================================================================
STEP 4 — WHAT STAYS UNRESOLVED
================================================================================
WHAT PLACES THE BOOTLOADER AT ADDRESS 0 BEFORE ANY PRESERVED IMAGE RUNS. No
code in the preserved set does it. A mask ROM was never searched and cannot be
(log 113 recorded the same boundary for cross-image calls), so this is a
boundary rather than an absence.

  IT DOES NOT BLOCK PATH B. A replacement never has to reproduce that stage,
  because the bootloader is precisely the component a replacement INHERITS. The
  unread stage hands address 0 to the bootloader; everything after that is now
  understood. The ADR's gate 5 is marked satisfied on exactly that reasoning.

ALSO UNRESOLVED, and each recorded rather than guessed:
  - the address-0 window's true extent (at least 0x10000, because the copy is
    that long, and the bootloader occupies 0x0..0xefff)
  - which physical memory backs it
  - whether it is a hardwired alias of some other range or a memory with its
    own decode — indistinguishable from code that never configures it
  - whether its contents survive the AIRCR reset: the design assumes so, and no
    code asserts it
  - who reads vector slot 7 back; the bootloader writes it and no preserved
    image is shown consuming it

  DISCIPLINE: the alias conclusion must be labelled strongly-inferred and not
  observed, because it rests on a would-destroy-itself argument; no claim may
  name the backing memory; no claim may say the ROM stage is understood; and
  the replacement advice must contain no flashing verb. Each has an
  anti-vacuity companion.

  FAIL-CLOSED: a missing slice and a missing census each raise; bodies()
  raising makes main() return 1 without a traceback.
