5. 51 21 -- REMAP ON THE BASE LAYER (answers protocol.md s9)
================================================================================
  03   04:29:10.337  51 21 2f 00 11 00 1c    (source X = 47; target not noted)
  03b  04:57:49.721  51 21 10 00 39 00 15    owner: "Tab to Right Shift"
Byte 2 source 0x10 = Tab (protocol.md index 16). BYTE 3 IS 0x00: a base-layer
remap is the SAME subcommand as the Fn-layer one with 0x00 where the Fn layer
carries 0x9f, exactly the map's "byte 3 in {0x00, 0x9f}". protocol.md s9
asked "whether a base-layer write uses a different subcommand than 51 21":
it does not.
BYTE 6 IS THE KEY'S CURRENT ACTUATION, not a constant: 0x15 = 2.1 mm in 03b
(actuation had just been set to 2.1) and 0x1c = 2.8 mm in 03 (set to 2.8 two
minutes earlier). protocol.md's historical 0x0A was the 1.0 mm default.
Target 0x0039 = Right Shift. The AC profile stores the same remap as
keyfunction_0_2 target_key 512 -> 1034, button_function 0 -> 1.

6. 54 -- THE MACRO UPLOAD, DECODED
================================================================================
6.1 When. SAVING a macro in AC's editor sends NOTHING: no vendor frame at all
between 04:57:49 and 04:59:40 (macro 03 saved 04:58:41 per its file mtime)
nor between 05:02:34 and 05:03:34 (macro 04 saved 05:03:02). Run 03's two
macros (Macro01/02, 04:30) never reached the wire and were never assigned.
The macro goes to the keyboard only when it is ASSIGNED to a key:
  05:01:59.989  51 18 01 00 00 00
  05:02:00.253  54 00 0d 00 2e 00 00 00 00 <records>      Macro03 -> Z
  05:03:43.572  51 18 01 00 00 00
  05:03:43.648  54 00 0c 00 10 00 00 00 00 <records>      Macro04 -> Tab
each preceded by a burst of 22-24 `12 12` queries, all replying 12 12 00 00
01 01 (the map's failure branch of 12 12/12 13).

6.2 Layout. byte 2 = number of 4-byte records INCLUDING the terminator;
byte 4 = the assigned key as a source index (0x2e = Z = 46, 0x10 = Tab = 16);
records start at byte 9; each record is
      <key> <02 press | 01 release> <delay, u16 little-endian, ms>
and the list ends with 0xff.

6.3 Proof against AC's own file. Macro03.GMAC is plain text:
      Press,A,30,65 / Delay,119 / Release,A,30,65 / Delay,424 / ...
Record by record against the wire:
      1f 02 77 00  Press A,   119 ms      1f 01 a8 01  Release A, 424
      20 02 63 00  Press S,    99         20 01 1e 02  Release S, 542
      21 02 41 00  Press D,    65         21 01 7d 0b  Release D, 2941
      1f 02 6a 00  Press A,   106         1f 01 80 01  Release A, 384
      32 02 6a 00  Press B,   106         32 01 b2 01  Release B, 434
      30 02 61 00  Press C,    97         30 01 00 00  Release C, (none)
      ff
All eleven delays match. 12 records + ff = 13 = byte 2. Macro04 (A x5)
matches all ten delays the same way (134 432 122 453 99 474 127 1712 71
3128); its file then ends "Press,Left Click,301,301" and the wire carries one
record f0 12 00 00 before ff: 10 + 1 + 1 = 12 = byte 2. So a mouse left-click
press encodes as f0 12 -- one sample, not generalised.
The GMAC's own numbers (A 30, S 31, D 32, B 48, C 46) are Windows scan codes
(A = 0x1E ...), NOT the wire's key numbers.

6.4 51 18 01. The map's "=MS_A" handler (stores bytes 2 and 4). Here it
always precedes a 54 upload with byte 2 = 01, byte 4 = 00. Consistent with a
macro-setup step; the name is NOT established.

6.5 In the AC profile the macro is a FILE PATH, not the events:
  keyfunction_3_7 -> ...\CachedMacroProfiles\Macro03.GMAC  (button_function 3)
  keyfunction_0_2 -> ...\CachedMacroProfiles\Macro04.GMAC
The events live only in the .GMAC and, after assignment, on the keyboard.

7. KEY INDEX TABLE, ROW 3 -- A CONFLICT WITH protocol.md s4
================================================================================
protocol.md s4's table is 1-based row-major, "directly confirmed" at seven
keys and EXTRAPOLATED for the other 61. Section 6.3 names the letters (from
the GMAC) against the wire numbers:
  A = 0x1f (31)   S = 0x20 (32)   D = 0x21 (33)   B = 0x32 (50)   C = 0x30 (48)
The table gives A = 32, S = 33, D = 34 (Caps = 31), B = 50, C = 48.
Rows 2 and 4 agree (also Tab 16 and Z 46 from section 6.2). ROW 3 IS OFF BY
ONE: the wire puts A where the table puts Caps. The table's confirmed Enter =
43 means row 3 cannot simply shift down by one without another key between
' and Enter or Caps sitting elsewhere. NOT RESOLVED. The six rapid-trigger
keys (12 20 21 1f 2e 2c) read as W S D A Z + one more under the wire
numbering, which would suggest the owner's test keys; the owner did not
record them.
The macro upload is a SAFE way to map every key: record keys in a macro,
assign it, and read wire number against the GMAC name. Run 03c uses this.

10. TOOLS -- FIRST WINDOWS RUNS (tools/README.md asks for these to be logged)
================================================================================
10.1 USBPcapCMD is a GUI-subsystem executable. PowerShell's `&` neither waits
for it nor captures its stdout: the capture-03 prompt returned in 10 ms,
Ctrl+C never reached it, and `--extcap-interfaces` / `--extcap-config`
output is empty when read through `&`. `cmd /c` both waits and captures.
Capture 03 was therefore stopped with Stop-Process from an elevated shell.
This affects any script that invokes USBPcapCMD with `&`.

10.2 tools/feature-session.ps1 -- NEW, first run = capture 03b. Starts
USBPcapCMD in the background with 03's flags, finds the keyboard's
interface by probing \\.\USBPcap1..16 through `cmd /c`, marks each owner
action by Enter with ms timestamps, snapshots the AC profile folder before
and after, checks REV before and after, stops the capture itself, verifies
the pcap magic and prints the sha256. First attempt failed at interface
detection (10.1); fixed; second attempt produced 03b.

10.3 tools/snap-config.ps1 -- FIRST WINDOWS RUN FAILED, FIXED.
  error : Cannot find an overload for "ToString" and the argument count: "1"
  cause : Get-ProfileFiles returned `,$files`. `foreach ($f in
