================================================================================
Not a second near-miss of the same kind. A different data structure.

$ read 0x5674 onward as 12-byte records {uint32 exponent, uint32 hi, uint32 lo}

  0x5680 exp=0x4005 (e=  6) mant=0xc800000000000000   = 10^2
  0x568c exp=0x400c (e= 13) mant=0x9c40000000000000   = 10^4
  0x5698 exp=0x4019 (e= 26) mant=0xbebc200000000000   = 10^8
  0x56a4 exp=0x4034 (e= 53) mant=0x8e1bc9bf04000000   = 10^16

  Field 0 is an x87 80-bit EXPONENT: 0x3fff + the binary exponent. It is not an

  a 24-byte stride walked every OTHER 12-byte record and found three.

  The surrounding bytes settle the context beyond argument:
  0x5614 "0123456789ABCDEF" 0x5624 "@0X" 0x5627 "0123456789abcdef" "@0x"
  0x5660 "0123456789ABCDEF" "XP"  — the printf integer/float digit tables.

FINDING 1, STEP 4 — THE RULE THAT REPLACES THE SHAPE RULE
================================================================================
tool/find_pointer_tables.py now keeps THREE things apart that log 104 collapsed
into one. There is no hard-coded address anywhere in the tool.

  1. POINTER-SHAPED RUN. The old rule, unchanged: at least three Thumb-looking
     words at a constant stride, each naming an even address at or above the
     image's code floor. Reported, and nothing more. A shape is not evidence.

  2. VALIDATED DISPATCH / CALLBACK TABLE. A run whose words CODE ACTUALLY READS:
       (a) an instruction inside a real Ghidra function body performs a
           PC-relative literal load of the entry's address (LDR T1 or LDR.W T2);
       (b) the loaded value is stored into a structure field (STR T1 or
           STR.W T3);
       (c) some function performs `ldr rX,[rY,#off]; blx rX` on that same field
           offset.
     A run whose span is >= 75% printable text is REJECTED as string/data before
     any of that is considered.

  3. ELIGIBLE REACHABILITY ROOT. A validated table, and nothing else.

Three things are explicitly NOT accepted as grounds, because each of them
admitted 0x1404:
  - "it contains three pointer-looking words";
  - "the vendor image has the same run at the measured -0x2c shift" (so does
     the format-string block: the strings relocate too);
  - "Ghidra can disassemble code at the targets" (the seed created that code).

The instruction scan decodes ONLY the ordered body ranges Ghidra reported, so
literal pools and inline data — the very bytes being judged — are never decoded
as instructions. A table read by code Ghidra never disassembled would score as
unconsumed, which keeps it a candidate: the safe direction.

FINDING 3 — capture.ps1 COULD OVERWRITE EVIDENCE AND REPORT FALSE SUCCESS
================================================================================
REPRODUCED from the file: `& $tshark @a` followed unconditionally by
`Write-Host "saved: $Out"`. No Test-Path on $Out before launching, no
$LASTEXITCODE check, no size or content check, and $Interface accepted any
string without comparing it to `tshark -D`'s output. tools/README.md already
recorded the consequence: "the original first-launch capture was lost that way".

CORRECTED:
  - an existing -Out is REFUSED, before tshark is launched;
  - there is NO -Force. A switch that puts evidence destruction one keystroke
    away is the same hazard with a longer name. -Unique gives a timestamped
    filename instead, which is the preferred route;
  - requested interfaces must appear in the enumerated list, or the run stops;
  - $LASTEXITCODE is checked for `tshark -D` and for the capture;
  - success requires exit 0 AND the file exists AND it is a regular file AND it
    is non-empty AND its first four bytes are a pcap or pcapng magic number;
  - only then is `saved:` printed, with the byte count and the SHA-256;
  - a failed run prints FAILED and removes the zero-byte stub; a non-empty
    partial capture is kept and said to be kept;
  - still passive: no keyboard command, no HID write, nothing sent.

TESTS: tool/windows_tools.py holds the rules and tool/test_windows_tools.py runs
them — 29 tests covering collision refusal, unique naming, unenumerated
interface, native failure, missing file, zero-byte output, non-capture output,

FINDING 5 — haltrace.ps1 SESSION INTEGRITY
================================================================================
REPRODUCED. `$line | Tee-Object -FilePath $Out -Append` with no collision check.
Missing elevation produced Write-Warning and continued. CreateFileMapping was
tested only for a NULL return — but it SUCCEEDS when the object already exists
and reports that only through GetLastError == ERROR_ALREADY_EXISTS (183), which
the script never read; it then fell back to a local name, which sees none of the
session-0 service output the tool exists to read. Handles were released only in
the finally block, so a failure between CreateFileMapping and MapViewOfFile leaked.

CORRECTED:
  - an existing -Out is refused (-Unique available), because appending a second
    experiment to a first makes both unattributable;
  - missing elevation EXITS;
  - Global\ only, no local fallback;
  - GetLastWin32Error is read after the mapping and after BOTH events, and
    ERROR_ALREADY_EXISTS aborts rather than racing DebugView for messages;
  - Close-All releases every handle on any partial-initialisation failure;
  - completion prints the line count, the output size and the SHA-256.

THE LIMITATION THAT REMAINS, STATED RATHER THAN FIXED, in the script and in
tools/README.md: DBWIN has ONE slot and no queue. A message emitted before the
listener starts, or between its Wait calls, is lost even when this process is
the sole listener. A MISSING LINE IS NOT EVIDENCE THAT A HAL CALL DID NOT HAPPEN.
