STEP 1 — WHY A SECOND BUILDER RATHER THAN A REWRITE
================================================================================
tool/build_modified_image.py is locked to the vendor 1.00.58 artefact and is the
subject of log 77. Rewriting it would invalidate that log's reproducibility for
no gain. The plan permits "extend or replace"; this is the extension:

  tool/build_offline_image.py    the general builder, two explicit adapters
  tool/build_modified_image.py   unchanged, still passing its own tests

Nothing is duplicated that already exists. The new builder reuses
falchion_image's parser, allowlist, `chunked_crc_sum` and `word_sum`, and
analyze_boot_structures' `known_boot_checks` and `UNRESOLVED` list.


================================================================================
STEP 2 — THE ADAPTERS, AND ONE ADDRESS-SPACE BUG THEY CAUGHT
================================================================================
  vendor-1.00.58-full          base 0x00000  size 0x7c000
  installed-1.59-application   base 0x10000  size 0x6c000

Every offset in the builder is a LOGICAL FLASH offset translated through the
adapter's base. THE ADAPTER IS CHOSEN BY MATCHING THE SOURCE'S HASH AND SIZE
AGAINST THE ALLOWLIST — there is no `--base` flag, so a wrong base cannot be
supplied. A test asserts the string "--base" appears nowhere in the module.

A BUG THIS DISCIPLINE CAUGHT DURING DEVELOPMENT, recorded because it is the
same class of error logs 110 and 114 already found. The first draft compared a
patch's logical offset against `record.addr` directly, and every patch was
refused as "outside every record". A record's address field carries the
0x60000000 flash base:

    slot 0: addr=0x60011000 len=0x058ac dst=0x18000000
    slot 1: addr=0x60021000 len=0x1e754 dst=0x18000000

The translation now happens once, in `active_records()`, which returns `Span`
objects in logical offsets. Nothing downstream ever sees a raw address field.

STEP 4 — A PATCHED BUILD, AND THE DEPENDENCY ORDER
================================================================================
Exercised with a byte inside record slot 1. THIS IS NOT A PHASE 8 TARGET
SELECTION — it is a functional exercise of the builder, and Phase 8 remains
unstarted.

  ADAPTER vendor-1.00.58-full base=0x0
  OUTPUT  vendor-1.00.58-full_demo_UNTESTED_ee0a2ea68483.bin
          sha256=ee0a2ea684833d080f74a949d153e9bc95f316489822af8abda8905746198783
  PATCHES 1
    0x3f66f 52 -> 72
  RECOMPUTED 2
    record_chunked_crc at 0x1003c = 0x4ec85064
    application_word_sum at 0x7bffc = 0xb17954f7
  WORD SUMS
    application: available
    backup_bootloader: available
    primary_bootloader: available
  VALIDATIONS 25
    failed: none

THE ORDER IS ENFORCED BY CONSTRUCTION, not by comment. The record CRC field at
0x1003c lies inside the application word-sum's covered range [0x10000,0x7bffc),
so computing the word-sum first would leave it stale. A test asserts that
containment explicitly, then verifies the stored word-sum against an
independent recomputation — so the test would fail if the order were reversed.

A patched build changes at most 1 + 4 + 4 bytes: the patched byte, the record's
CRC field, and the word-sum. A test pins that bound.

NOTE THAT SEVERAL REFUSALS GIVE TWO REASONS. That is deliberate: `reject_reasons`
collects every applicable reason rather than returning the first, so a reviewer
sees that a bootloader-region patch is refused on region grounds AND on
record-containment grounds independently.

POLICY-GATED PATHS. The backup-bootloader word-sum recompute exists and is
UNREACHABLE by default: any patch overlapping [0x61000,0x71000) is refused
before it, and no reviewed policy permits that region. The primary-bootloader
word-sum is in neither the permitted nor the policy-gated list; on an installed
source it is reported UNAVAILABLE, is never recomputed, and appears in the
manifest's unresolved risks. Tests pin all three positions.

================================================================================
STEP 7 — INDEPENDENCE OF THE VALIDATORS
================================================================================
Requirement 11 says the checkers must not import the builder's mutation
functions. tool/test_build_offline_image.py reimplements both integrity
algorithms from `zlib` and `struct` directly:

    independent_chunked_crc()   the per-0x10000-chunk CRC-32 sum, written from
                                the log-75/76 description
    independent_word_sum()      the additive 32-bit word sum

Three tests use them: the record CRC matches, the application word-sum matches,
and the word-sum covers the updated CRC field. A bug shared between the builder
and its checker cannot hide behind these, because they share no code.

================================================================================
UNRESOLVED
================================================================================
  - The builder verifies STRUCTURE. It cannot verify that an image boots, and
    it says so in every manifest.
  - The primary-bootloader word-sum is unavailable on an installed source and
    is never recomputed. An application-region patch does not depend on it,
    which is why that is a limitation rather than a defect — but a build that
    needed it would be refused, not approximated.
  - `known_boot_checks` is run and reported, but the boot-structure UNRESOLVED
    list (what makes address 0 writable, which physical keys the recovery scan
    matches, any ROM stage ahead of the bootloader) is carried into every
    manifest unchanged. Those are still open.
  - No new record can be added. The record table is a fixed eight slots and
    the rules for adding one are not proven, so the builder does not offer it.
