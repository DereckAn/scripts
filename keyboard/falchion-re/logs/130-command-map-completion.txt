STEP 2 — BLOCK D
================================================================================
The reader is the whole layout:

    18005830  eb0a 0741   add.w  r7,r10,r1,lsl #1   r10 = BLOCK D, r7 = +i*2
    18005834  797a        ldrb   r2,[r7,#0x5]       entry i, byte +1: FLAGS
    18005836              lsrs   r2,r2,#0x3         bits 3..7 -> active?
    18005840  f897 c004   ldrb.w r12,[r7,#0x4]      entry i, byte +0: VALUE
    18005844..1800584e    scan an existing byte list for that value
    18005852..18005856    append i and bump the count only if not present
    1800585a  29f7        cmp    r1,#0xf7           247 ENTRIES

    offset   size    type                role
    +0x000   2       u16                 the block's own additive checksum —
                                         log 125's shape for every stored
                                         block; read nine times and written
                                         once, all in FUN_18000d56
    +0x004   0x1ee   247 x 2-byte entry  {+0: value byte, +1: flags byte}
    +0x1f2   0x1ee   247 x 2-byte entry  the second table

  AND THE ARITHMETIC CLOSES: 4 + 0x1ee = 0x1f2, and 0x1f2 + 0x1ee = 0x3e0, the
  block's declared size, exactly. 247 is log 125's key-table entry count
  ("FUN_1800072c fills 0x1ee entries: indices 0..0xf6"), and two equal tables is
  the same two-table shape as the profile block's key tables at +0xd4 and
  +0x2c2. WHICH INDEX SELECTS WHICH TABLE IS NOT ESTABLISHED — the reader walks
  one of them.

  WHAT THE DIVIDE-BY-EIGHT READER DOES WITH IT: once per tick-job pass it
  builds a DE-DUPLICATED list of the entries whose flags bits 3..7 are set,
  keyed by their value byte. It is an active-set pass, not a per-key lookup.

  DEFAULTS: NOT RECOVERED. The block is zero-initialised RAM in the image, so
  no static default is readable, and 51 56 restores it through 0x180005c6 and
  0x1800aadc, neither traced here.

  WHAT PERSISTENCE MEANS: log 125's flash home is 0x340000 + profile*0x1000 —
  one 0x3e0 block per profile, six profiles. With the layout, that is a
  per-profile per-key table of 247 two-byte entries surviving a power cycle and
  re-read into RAM on profile load, like the keymap bank and the profile block.

  ARMOURY CRATE MATCH: NONE IS CLAIMED. Log 125's decode leaves no 247-entry
  two-byte-per-key structure unmatched, and matching on size alone is precisely
  the resemblance rule this project forbids.

STEP 3 — THE DUAL-ROLE TIMER, AND A CORRECTION
================================================================================
MECHANISM: dual-role, hold-to-alternate, threshold in 10 ms units.

  the threshold  record +0x22 of the key*0x20 array — offset +0x02 of the
                 record one stride on
  the payload    the halfword at the same record +0x20
  the scaling    threshold x 10 x (1 << rate index) tick-job invocations, which
                 log 127 showed is threshold x 10 ms at either polling rate
  on expiry      the halfword is appended to a bank and the bank's index bumped

THE BANK, and this is where log 128 was wrong:

    base       0x18024000
    stride     600 bytes = 300 halfword slots
    arithmetic k*15, then *5, then <<3 — the writer at 0x180054c8..0x180054d2
               and the consumer at 0x18006084..0x18006094 compute it IDENTICALLY
    index      a per-bank word counter, read and incremented in place
    consumer   FUN_180061c2, the report builder — veneer 0x4076, the last call
               in log 127's rate-gated tick block:
                 18006094  eb09 00c0   add.w  r0,r9,r0,lsl #3
                 1800609c  f830 0012   ldrh.w r0,[r0,r2,lsl #1]
                 180060a4  42a8        cmp    r0,r5

  THE CONSUMER COMPUTES THE SAME STRIDE FROM TWO DIFFERENT INDICES — one at
  struct +0x80 and one at +0x7c — and compares the two banks entry by entry,
  setting a change flag when they differ. THAT IS A CURRENT/PREVIOUS DOUBLE
  BUFFER. Log 128 called 0x18024000 + k*600 "a per-layer output ring"; THE
  PER-LAYER READING IS WITHDRAWN. k is a bank selector.

WHAT IS STILL OPEN, stated rather than filled in:
  - WRAP: none found. The writer increments the counter with no modulo and no
    bound test at the append site; the consumer stops at 120 (cmp r1,#0x78).
    Whether anything resets the counter each pass is NOT established.
  - RELEASE BEFORE EXPIRY: NOT ESTABLISHED. The append is on the expiry branch
    only; no reset of the per-key counter on release was traced and the tap-side
    path was not followed.
  - WHICH COMMAND SETS THE THRESHOLD: NOT ESTABLISHED. The located subcommands
    write record +0x04, +0x06, +0x07, +0x08, +0x0a, +0x0e and +0x0f; NONE was
    shown writing +0x00 or +0x02, which is where the payload and the threshold
    live.

NO HAL NAME IS ASSIGNED, and a test enforces it. The candidates remain
ChangeKey_ModTap, ChangeKey_Toggle, ChangeKey_DKS and SetSpeedTap; that needs
the capture, not the listing.
