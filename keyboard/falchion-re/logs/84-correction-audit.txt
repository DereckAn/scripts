=== DEFECTS FOUND AND FIXED ===
1. FATAL, backup_firmware.py: the per-chunk sequence queued all five
   reports and then performed a single read(), so the 0x8f status reply
   was consumed as if it were the 0xaa read data. Every chunk would have
   been wrong and no response was validated at all. Replaced with immediate
   request-response exchanges.
2. backup_firmware.py selected the first PID-1b7f hidraw node without
   inspecting its report descriptor.
3. backup_firmware.py wrote its output with no post-dump validation, so
   three identical-but-wrong passes would have been accepted.
4. A transport close() error could mask the protocol error that preceded it.
5. FINDINGS.md cited 0x61000 as a duplicate checksum offset; 0x61000 is the
   start of the duplicated bootloader region, not a checksum offset.
6. TIMELINE.md claimed a live refusal against the app-mode device that was not
   supported by log 83. This correction audit later exercised only the new
   flag-gated refusal path, before device selection.
7. The repository-root CLAUDE.md carried an unrelated appended block.

=== PROTOCOL EVIDENCE USED (static, logs 81-82) ===
log 81 FUN_00002db8, command byte 0x05:
    *(+0x38) = (*(+0x38) & 0xfd) + 2;   // set busy bit 1
    FUN_00003b64();                     // synchronous READ
    *(+0x38) = *(+0x38) & 0xfd;         // clear busy bit 1
    *(+0x34) = 0;                       // clear pending command
  Erase (0x01) and program (0x51) use bit 0 identically, so bit 1 is
  specifically the READ indicator.
log 82 FUN_00003740: resp[0] = query & 0x7f, so 0x8f -> 0x0f, 0xaa -> 0x2a.
  Status 0x0f returns resp[1] = state+0x38 and resp[2] = state+0x35.
  Data 0x2a memcpys the payload starting at resp[1] for the set length, so
  response[1:1+length] skips the response code, not a report-ID prefix.

UNRESOLVED post-EXEC scheduling race: the 0x1f parser only sets the pending
byte state+0x34; the service loop (FUN_00003a7c -> FUN_00002db8) is what
sets bit 1 and performs the READ. Nothing recovered proves the service loop
has run before the host's first 0x8f. In that window bit 1 reads clear and
0xaa could return the previous chunk's buffer. Status does not expose
state+0x34, so the host cannot distinguish 'finished' from 'not started'.
No timing guarantee is claimed. The end-of-dump self-validation below is a
mitigation, not a proof of correctness.
