STEP 1 — WHY THE VECTOR HANDLERS HAD TO BE SEEDED
A raw binary import gives Ghidra no reason to treat a vector-table word as
a code reference, so a handler that nothing calls is never disassembled and
never becomes a function. Before seeding, none of the handler addresses
existed as functions, every reachability root failed to resolve, and the
context column came back empty for all 80 functions.

STEP 4 — WHAT THE WRITTEN VALUES SAY
$ python3 tool/map_hardware_interfaces.py | sed -n '/^NOTABLE_OBSERVATIONS/,/^COVERAGE/p'
  NOTABLE_OBSERVATIONS 8
    The NMI handler requests a system reset.
      basis: AIRCR is written 0x05fa0004: the architectural VECTKEY 0x05fa with SYSRESETREQ set. Written from the NMI context.
      confidence: high — the value and the register are both architectural
    The timebase pends a software interrupt, which is the shape of a preemptive scheduler.
      basis: ICSR is written 0x10000000 (PENDSVSET) from the SysTick context, and the PendSV vector points at its own handler.
      confidence: high for the mechanism, none for what the scheduler schedules
    The application also pends that software interrupt, from several sites.
      basis: ICSR is written 14 times in the application image, including from an interrupt context.
      confidence: high for the mechanism
    The interrupts the software enables are the ones the table actually populates: IRQ6, IRQ38.
      basis: NVIC_ISER words written with those bits set, cross-checked against the vector slots that hold a non-default handler. Two independent parts of the image agree.
      confidence: high
    The fault handler reads the architectural fault status and address registers rather than just hanging.
      basis: CFSR, MMFAR and BFAR are all read from the HardFault context.
      confidence: high — all three registers are architectural
    Two identical unnamed blocks are unlocked with a magic key on the reset path.
      basis: 0x40008000 and 0x40009000 are each written 0x5afa0000, and 0x4000800c and 0x4000900c are each written 0x5afa55aa. A key-protected register pair, duplicated. What the blocks control is not established.
      confidence: high for the pattern, none for the identity
    A reset-path register is programmed with the flash address of SN_FWIN record slot 1.
      basis: 0x4002f004 is written 0x60021000, which is exactly record slot 1's address from the installed header. The register is therefore tied to the image layout, whatever else it does.
      confidence: high for the correspondence, none for the register's purpose
    The unnamed block at 0x40100000 is the one the live interrupt serves.
      basis: 19 registers, 126 accesses, touched from IRQ6,called from entry image 0x1994 — that is, from both an interrupt handler and the initialiser the entry image calls. It is the application's principal peripheral. Naming it would require a reference manual.
      confidence: high for the association, none for the identity

PHASE 3 REGENERATED — SEEDING CHANGED THE FUNCTION SET
Seeding roughly doubled the analysed function set, so every Phase 3 number
derived from it had to be recomputed. Doing that exposed a real flaw in the
Phase 3 method: data spans were paired by list index, guarded only by the
two sides having equal span counts. With the larger function set the counts
still matched while the k-th spans described different regions, so the
pairing silently drifted.

The fix is referential rather than positional. Each uncovered span is keyed
by the matched function that precedes it, and a pair is compared only when
the anchor key, the distance past that anchor and the length all agree on
both sides. Anything else is reported and left uncompared, so a mispaired
span can no longer be diffed.

FACTS ESTABLISHED IN THIS PHASE
  1. The vector table is 73 slots at entry-image 0x0..0x124: 16 ARMv7-M
     core vectors plus 57 external interrupts. Unused slots are filled with
     the default handler 0x000014df, which is what bounds the table; the
     first code address is 0x140. Initial SP 0x18036168, reset 0x000014a9.
  2. All six fault-class vectors plus SVCall, PendSV and SysTick are
     populated with distinct handlers.
  3. Eight external interrupts carry a non-default handler: IRQ3 in the
     entry image, and IRQ6, IRQ31, IRQ32, IRQ36, IRQ37, IRQ38 and IRQ48 in
     the application image. So the entry image owns the table while the
     application owns most of the handlers, and the table's application
     addresses are only valid after the scatter load.
  4. Software enables exactly IRQ6 and IRQ38 through NVIC_ISER0/1, both of
     which hold a non-default handler in the table. Two independent parts
     of the image agree.
  5. The NMI handler writes AIRCR 0x05fa0004 — VECTKEY with SYSRESETREQ —
     so NMI requests a system reset.
  6. SysTick writes ICSR 0x10000000 (PENDSVSET) and the application writes
     it 14 more times. A timebase pending a software interrupt with a
     populated PendSV vector is the shape of a preemptive scheduler.
  7. The HardFault handler reads CFSR, MMFAR and BFAR, so it reports faults
     rather than merely hanging.
  8. Two identical unnamed blocks at 0x40008000 and 0x40009000 are each
     written 0x5afa0000, with 0x5afa55aa written at +0xc, on the reset
     path: a magic-key-protected register pair, duplicated.
  9. Reset-path register 0x4002f004 is written 0x60021000, exactly SN_FWIN
     record slot 1's address from the installed header.
 10. The unnamed block at 0x40100000 — 19 registers, 126 accesses — is the
     one IRQ6 serves, touched from both IRQ6's handler and the initialiser
     the entry image calls. It is the application's principal peripheral.
 11. The entry image transfers control into the application through exactly
     two non-vector code pointers, 0x18016e69 and 0x18016f2d.

WHAT THIS PHASE DOES NOT ESTABLISH
  * No vendor peripheral is named. Four of the plan's seven analysis areas
    — USB, GPIO/scan, Hall-effect/ADC, RGB — and the nonvolatile write path
    are reported not-covered, because identifying a block needs a SNC73270
    reference manual that this repository does not have. Nothing here
    supports any claim about actuation thresholds or rapid trigger.
  * The register list is a lower bound. An access is reported only when
    constant propagation resolved its base register; accesses through a
    pointer in a parameter or structure are counted as unresolved.
  * Reachability follows Ghidra's call graph, which does not follow calls
    through function-pointer tables. The application image therefore has
    479 of 530 functions unreached: its task entry points are dispatched
    through tables (logs 48, 49, 65), not called directly.
  * The interrupt-to-peripheral wiring is unknown. Knowing that IRQ6 is
    enabled and serves the 0x40100000 block says nothing about what that
    block does.
