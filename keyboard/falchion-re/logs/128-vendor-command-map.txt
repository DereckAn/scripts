================================================================================
THE HEADLINE
================================================================================
THE SURFACE IS FAR LARGER THAN THE CAPTURE RECORD. notes/protocol.md's command
table has six rows. The dispatcher accepts SEVENTEEN TOP-LEVEL OPCODES and
TWENTY-FOUR 0x51 SUBCOMMANDS and TEN 0x12 QUERIES, every one of them located at
a compare site pinned to the image.

AND MOST OF IT IS STILL NOT DECODED, which is the honest headline. Of the 34
0x51 subcommands and 0x12 queries:

    wire-proven             9    observed in log 126's capture AND decoded
    static-handler-proven  12    reads, ranges and stores read out of the
                                 instruction stream; no capture exercised them
    static-located-only    13    the compare site and handler entry are proven
                                 and NOTHING ELSE IS

Eleven of the seventeen top-level opcodes are not opened at all. A surface that
is bounded is not a surface that is understood, and the model says which is
which on every row.

THE FIVE ANSWERS THE STEP WAS ASKED FOR:

  PROFILE SWITCH   there IS a USB command, and it is INDIRECT. `51 00` posts a
                   request; the storage state machine writes the byte.
  MACRO BLOCK      it DOES have a USB writer. Macros are not device-only.
  BLOCK D          it does NOT. Its only writer is the storage state machine.
  THE +0x22 FIELD  a per-key press-and-hold timer that emits a stored 16-bit
                   code on expiry — a dual-role key. NO HAL NAME IS ASSIGNED.
  THE NINE WRITES  nothing else was being re-applied. All nine are `51 31`
                   index 0, and the map is what makes that a real negative.

STEP 0 — METHOD, AND THE TWO REGISTERS THAT UNLOCK EVERYTHING
================================================================================
Sources: ghidra/decompiles/dispatcher.txt and ghidra/peripherals/*.txt, both
pre-existing and read-only; the imported slices, for byte-level confirmation;
and notes/polling-rate-protocol.json and notes/profile-format.json, read as
models rather than restated.

TWO REGISTERS ARE SET ONCE AT DISPATCHER ENTRY AND NEVER REASSIGNED, and every
handler below is legible only because of them:

  18001fc2  4c6c        ldr   r4,[pc,#0x1b0]   ; *(...) = 0x180233a8
                                               ; THE 64-BYTE REQUEST BUFFER
  18001fd6  2601        movs  r6,#0x1          ; the default response length
  18001fdc  f1a9 0905   sub.w r9,r9,#0x5       ; r9 = 0x1801e6b4
  18001fee  f109 071c   add.w r7,r9,#0x1c      ; r7 = 0x1801e6d0
                                               ; THE 16-BYTE DEVICE HEADER

So `[r4,#N]` is request byte N and `[r7,#6]` is THE CURRENT PROFILE — log 125's
selection byte. Every handler that indexes a per-profile structure does it
through r7+6, and that is what makes the per-profile writes identifiable.

CONFIDENCE SCHEME, applied per row and never by feature name alone:
  wire-proven / static-handler-proven / static-located-only / hal-name-only.

STEP 2 — PROFILE SWITCHING, ANSWERED IN FULL
================================================================================
THE QUESTION was whether a USB command stores the selection byte at device
header +6, and if not, to prove the negative by enumerating its writers.

THE ANSWER IS NEITHER OF THE TWO OFFERED. There IS a USB command, and it does
NOT write the byte.

  $ every resolved access to 0x1801e6d6 in the installed export
      97 reads
       2 writes — 0x180011bc and 0x18001df8, BOTH in FUN_18000d56
       0 writes from the dispatcher, in any of its 13 accesses

  THE DISPATCHER ONLY EVER READS IT. The write happens in the storage state
  machine, and the chain is:

    host      51 00 xx xx <profile>, accepted 0..5 with 6 folded to 0
    handler   0x18002514 posts opcode 2 at REQSTRUCT+0x84 and the profile at
              +0x85, and only while +0x84 is not already 2
    machine   FUN_18000d56:
                180011b8  f898 0001  ldrb.w r0,[r8,#0x1]   ; REQSTRUCT+0x85
                180011bc  71a0       strb   r0,[r4,#0x6]   ; DEVICE HEADER +6
    read-back 12 00's reply byte 6 returns it, 0 reported as 6

  SO THE WIRE NUMBERING IS 1..6 (with 0 accepted as an alias for 6) WHILE THE
  INTERNAL INDEX IS 0..5. That asymmetry is visible in two places at once — the
  fold at 0x18002516 and the report at 0x180020ae — which is why it is stated
  as a protocol fact rather than as an inference from one site.

  DOES A SWITCH TRIGGER THE RELOAD? The four profile-apply writes of the
  polling-rate multiplier log 127 found — 0x1800117c, 0x18001548, 0x180018f8,
  0x18001ece — are all in FUN_18000d56, the same function that writes the
  selection byte at 0x180011bc, and 0x1800117c is forty bytes away from it.
  WHICH BRANCH A SWITCH TAKES IS NOT ESTABLISHED, so this step does not claim
  that one switch invocation reaches 0x1800153a specifically. What it
  establishes is that the write and the reload live in one function and that
  no other function writes the byte.

  THE SECOND WRITER, 0x18001df8, stores 0x0 — the factory-default path, which
  log 125 showed calling the key-table and keymap default initialisers.

STEP 3 — THE MACRO BLOCK
================================================================================
0x180225fc, 0x664 bytes, 53 resolved accesses in the installed export.

  IT HAS A USB WRITER, so macros are NOT device-only and the negative the
  prompt offered does not hold:

    180035dc  7008        strb r0,[r1]            ; MACRO +0
    180035e0  71cd        strb r5,[r1,#0x7]       ; MACRO +7
    180035e2  f44f 71c8   mov.w r1,#0x190         ; 400 bytes
    180035e8  bl 0x1801bdc8                       ; cleared from MACRO +8

  So the block opens with an EIGHT-BYTE HEADER and a 400-BYTE BODY that is
  cleared as a unit. The code immediately above filters HID usages 0x39, 0x47,
  0x53, 0xe2 and 0xe8 — Caps Lock, Scroll Lock, Num Lock, Left Alt and log
  120's vendor code — down a separate path, which is a RECORDING filter rather
  than a playback one: those are the keys a macro recorder must not capture.

  WHAT IS NOT ESTABLISHED, and is not guessed: the entry size, the record
  count, and whether an entry holds timing as well as key codes. 400 bytes is
  the cleared extent, not a proven stride. AND WHICH 0x51 SUBCOMMAND REACHES
  0x180035dc is not established either — the site lies in the dispatcher body
  past 0x18003310 and this step did not resolve the branch.


================================================================================
STEP 4 — BLOCK D
================================================================================
0x1801fef8, 0x3e0 bytes, flash home 0x340000 + profile*0x1000 (log 125), 14
resolved accesses in the installed export.

  IT HAS NO USB WRITER. Its only writer is FUN_18000d56, at 0x18001be0. The
  dispatcher never writes it.

  ITS RUNTIME READER IS ON THE REPORT PATH. FUN_180057fe reads +0x4 and +0x5,
  and FUN_180057fe is veneer 0x406c — one of the four calls in the rate-gated
  tick block log 127 mapped. So block D is consulted while reports are being
  built, not only at load time.

  ITS FIELDS ARE NOT DECODED. What is established: it persists, the storage
  machine owns it exclusively, and two of its bytes are read per report cycle.

  A METHOD NOTE THAT CHANGED THIS ANSWER. My first run reported FIVE writers
  for block D. The census covers six exports, and the vendor application is
  based at the same 0x18000000 — so an unscoped range query silently merged two
  releases. Scoping to the installed export alone gives one writer. A test now
  asserts that the scoped result is strictly smaller than the unscoped one, so
  the mistake cannot recur silently.


================================================================================
STEP 5 — THE +0x22 PER-KEY TIMEOUT
================================================================================
Log 127 found the site: `threshold x 10 x (1 << rate index)` invocations of the
tick job, compared against a per-key counter, which works out to
`threshold x 10 ms` at either polling rate. What it did not establish was what
the timeout is FOR. The expiry path answers that.

  180054c4  8c13        ldrh   r3,[r2,#0x20]        ; the record's paired halfword
  180054c6  6800        ldr    r0,[r0]              ; the layer
  180054c8  rsb/add                                 ; r0 * 75
  180054d0  ldr    r1,[pc]  -> 0x18024000
  180054d6  ldr.w  r1,[r10,r0,lsl #2]               ; the ring's index
  180054da  f82c 3011   strh.w r3,[r12,r1,lsl #1]   ; APPEND the halfword
  180054de  1c49        adds   r1,r1,#0x1           ; advance the index

  SO ON EXPIRY A STORED 16-BIT CODE IS APPENDED TO AN OUTPUT RING at
  0x18024000 + layer*600. A per-key timer that emits a different code once the
  key has been held long enough IS A DUAL-ROLE KEY: one code on tap, another on
  hold. Confidence: STRONGLY-INFERRED.

  NO HAL NAME IS ASSIGNED, and a test enforces that. `ChangeKey_ModTap`,
  `ChangeKey_Toggle`, `ChangeKey_DKS` and `SetSpeedTap` all describe
  hold-to-emit behaviour and nothing in the recovered code distinguishes them.
  Naming it would be exactly the "match by feature name alone" the step forbids.

  NOT ESTABLISHED: 600 bytes per layer is 300 halfwords, and 75 keys times 8 is
  also 600, so whether the ring is indexed per layer or per scan group is
  undetermined.


================================================================================
STEP 6 — THE NINE RAPID WRITES AT t = 314..318
================================================================================
Read from log 126's own model rather than re-derived:

  count 9, window t = 314.2555 .. 318.198, indices {0},
  ONE distinct 64-byte payload: 51 31 00 00 00 followed by 59 zero bytes.

  THE ANSWER IS A NEGATIVE, AND IT IS THE MAP THAT MAKES IT ONE. With
  twenty-four subcommands enumerated, "Armoury Crate was re-applying something
  else in that burst" becomes a testable claim — and it is false. No 51 50, no
  51 2d, no 51 00, no 51 57. Log 126 established the capture's entire
  host-to-device vendor traffic is 74 frames; in this window they are nine
  identical rate writes and their nine commits, and nothing else.

  SO THE BURST IS NOT A BATCHED APPLY, and it cannot be cited as evidence that
  other subcommands accompany a rate change. Its CAUSE is still undetermined —
  the map rules out a multi-setting batch; it does not explain why one setting
  was written nine times in four seconds.

STEP 8 — THE TOOL AND THE TESTS
================================================================================
Added tool/map_vendor_commands.py — one data model, notes/
vendor-command-map.{json,md}, with --json, --write and --check. No new
dependency: the compare sites are asserted against image halfwords, the two
jump tables are decoded from image bytes, and the census and inventories are

$ python3 tool/map_vendor_commands.py
  RESULT vendor_command_map_ok=True checks=88

Added tool/test_map_vendor_commands.py — 38 tests in four groups.

  FAIL-CLOSED, six tests. A missing image raises; an address outside it raises;
  and — the one that matters for a map whose claim is COMPLETENESS — A LOCATED
  SUBCOMMAND WITH NO CURATED ROW RAISES rather than being emitted blank. The
  test removes 0x31's row and requires the table to refuse to build. The same
  for a query, and for a missing upstream model.

  THE EVIDENCE, twelve tests. Seventeen opcodes, twenty-four subcommands, ten
  queries; every compare site and every cited instruction pinned to the image;
  both jump tables decoded; THE VENDOR RELEASE ASSERTED TO HAVE THE SAME
  SEVENTEEN COMPARES; two writers for the selection byte and none from the
  dispatcher; the macro block's USB writer; block D's absence of one; the nine
  rate writes.

  ANTI-VACUITY, five tests. The census must be scoped to one export AND the
  scoped result must be strictly smaller than the unscoped one, which is the
  bug that produced a wrong block-D answer. The block filter must find
  accesses in BOTH blocks. THE DISPATCHER MUST BE SHOWN TO WRITE SOMETHING
  ELSE, so "it never writes the selection byte" is a real absence. And a wrong
  encoding must be caught: the test asserts 0x18001ffc is NOT the value I first
  wrote for it.

  DISCIPLINE, fifteen tests. Most of the table must stay labelled undecoded and
  every `static-located-only` row must SAY "NOT established" in words rather
  than merely wear the label; every `static-handler-proven` row must name a
  store; every 0x51 write is gated and no 0x12 query is; the hold timer gets no
  HAL name and must list more than one candidate; the unmatched HAL names are
  listed; the actuation match must contain the words "offered as a match, not
  as the command's name"; the polling-rate field must be marked unchecksummed;
  no frame may be constructed; the document must say no device was accessed.

FIVE CHECKS THAT FAILED FOR THE RIGHT REASON, all mine, all caught before
anything was written:

  - four cited instruction encodings were wrong from memory (0x18001fc2,
    0x18001ffc, 0x180024a4, 0x18002be8, 0x18002bee, 0x18003316). The byte-level
    assertions caught every one. This is why the citations are pinned rather
    than transcribed;
  - "block D has no USB writer" FAILED, reporting five writers, because the
    census query was unscoped across six exports and the vendor image shares the
    address range. Scoping fixed it and an anti-vacuity test now pins the
    scoping itself;
  - the vendor-release check failed 16/17 — which turned out to be one of my
    wrong encodings, not a real release difference. After the fix it is 17/17,
    and the only differing halfword in the whole entry region is a relocated
    `bl` offset;
  - three rows labelled `static-located-only` described proven stores. The
    discipline test that requires such rows to SAY "NOT established" caught the
    mislabelling, and they were promoted to `static-handler-proven` rather than
    the test being loosened;
  - `12 13` was located by a compare site and had no curated row, and the
    fail-closed guard refused to emit the table until it got one.
