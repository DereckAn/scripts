  * FUN_00003b64 (READ) reads its address at *(u32 *)(S - 0x1000), which is T+0.

    so its last reachable byte is T+0x1003 == S+3. The host therefore has NO
    write path into the READ response buffer at S+4.

=== 4. THE ANSWER: THE RACE IS PROVEN POSSIBLE, AND IS THE DEFAULT ===
Chaining the three verified facts:

  (a) the 0x1f parser sets S+0x34 and W+4, and never W+0        (0x0000397e)
  (b) FUN_00002db8 -- the only code that sets busy and performs the READ -- is
      reachable only from FUN_00003a7c, whose loop body is guarded by W+0
      (`b 0x00003aa8` at 0x00003a7e, then `ldr r0,[r0,#0x0]; cmp; bne`)
  (c) W+0 is written only by the SysTick handler at 0x000048d0

therefore an accepted EXEC does not start the READ; it waits for the next
SysTick interrupt. The READ then takes the duration of one flash transfer.

  Answer to "can status 0x8f be serviced after EXEC is accepted but before busy
  is set?"  YES, provably: the two are in different execution contexts, and
  nothing in the 0x8f path advances the service loop.

  Answer to "can data 0xaa return a previous chunk during that interval?"
  YES, provably: 0xaa copies S+4 unconditionally (0x000037e8), and S+4 is
  written only by FUN_00003b64, which has not run.

  Answer to "is the flash read synchronous or asynchronous?"  Synchronous with
  respect to the service loop and asynchronous with respect to the host. Inside
  FUN_00002db8 the call to FUN_00003b64 -> FUN_00003f08 submits a descriptor and
  then spins (`for (; param_5 != 0; param_5 = param_5 & 1) param_5 =
  FUN_00004fac(iVar1,0xffffffff);`) before busy is cleared and S+0x34 is zeroed.
  So S+0x34 == 0 implies the data is fully published. But the host cannot see
  S+0x34, and the whole sequence is deferred to a tick.

Magnitude. SYST_RVR is the static constant DAT_00007f9c - 1 = 0x000278d0 - 1 =
161999, so the tick period is exactly 162000 core clocks. The wall-clock value
is NOT statically determined: FUN_00004910 selects the core clock from
_DAT_4500000c & 7 at runtime -- 12000000 (DAT_00004998), 0x7fff, or a computed
PLL value -- so the period is a runtime property, in the low milliseconds. Two
independent hints point at 1 ms (the tick job FUN_00002e90 wraps its counter at
1000, a 1 s wrap; and 162000 clocks is 1 ms at 162 MHz), but that is an
inference, not a recovered constant.

Either way the ordering is decisive: the dispatch latency is one tick
(milliseconds) while the busy window is one 48-byte flash transfer
(microseconds). So:

  * "wait to observe busy set, then clear" is NOT a usable strategy. The host
    cannot sample often enough to land inside the busy window; it will read
    "clear" for "not started yet" and proceed. This is exactly what
    tool/backup_firmware.py did before this change, so every chunk after the
    first would have returned the previous chunk's 48 bytes.
  * A fixed delay is not recommended and is not used: the tick period is not a
    static constant in this image.

=== 5. SEARCH FOR AN OBSERVABLE COMPLETION MARKER: NEGATIVE, WITH ONE EXCEPTION
Searched for a generation counter, address echo, completion byte, sequence
number, or exposed pending flag:

  * generation counter / sequence number: absent. Nothing in the READ path
    increments anything. The only counter in the image near this code is
    FUN_00002e90's 0..999 tick counter at 0x18010e8c, which no query returns.
  * address echo: absent. T+0 is write-only from the host's point of view; no
    responder sub-command returns it. FUN_00003740 handles 0x02, 0x09/0x0a,
    0x0e, 0x0f, 0x2a and a default of "code then zeros" -- none echoes T+0.
  * completion byte: absent. S+0x39 is host-writable via OUT 0x7f and is read
    by nothing (no `#0x39` load exists against S).
  * pending flag: present in RAM at S+0x34 but exposed by no query.
  * over-reading S+0x34 through 0xaa: technically reachable, and REJECTED.
    The 0x2a responder copies S+0x36 bytes and does not clamp, so setting the
    length to 0x31 would place S+0x34 at resp[0x31]. But the length must be
    raised above 0x30 while a READ may still be pending, and FUN_00003b64 reads
    the length at dispatch time:
      - 0x31 is not 4-byte aligned, and FUN_00002f0c rejects a misaligned length
        ((param_2[0xc] & 3) != 0 -> return 4) while FUN_00003f08 ignores that
        return and still spins in FUN_00004fac -- a plausible main-loop hang.
      - the next aligned value, 0x34, would let the READ write flash bytes over
        S+0x35/0x36/0x37, and an arbitrary S+0x36 then becomes the responder's
        unclamped memcpy length -> stack overflow in FUN_00003740.
    Both are worse than the race. Not used.
  * a locked ERASE/PROGRAM as a pending probe: sound but not adopted. At
    0x000038f0 (sub-op 0x01) and 0x0000398e (sub-op 0x51) the lock bit is tested
    first, and with S+0x38 bit 7 clear the whole handler is
      0000393a  ldr  r0,[0x00003a68] ; 0000393c strb r1,[r0,#0x35]   (r1 = 2)
    i.e. exactly one byte written and no flash code reached -- so `1f 01` while
    locked would convert the invisible S+0x34 into a visible S+0x35 (2 if the
    probe was parsed, i.e. pending == 0; unchanged 0 if it was dropped). It is
    NOT adopted, because it requires backup_firmware.py to be able to construct
    an execute-ERASE report, and the tool's central safety property is that no
    such report has a construction path. Recorded here as recovered evidence.

=== 6. THE SYNCHRONISATION STRATEGY THAT IS BOTH SOUND AND READ-ONLY ===
Adopted: a buffer-change handshake, using only reports already on the tool's
read-only allowlist (0x20, 0x21, 0x1f/0x05, 0x8f, 0xaa).

Soundness argument, resting only on facts verified above:
  1. S+4 is written by FUN_00003b64 and by nothing else (section 2), and the
     host has no write path into it (section 1).
  2. FUN_00003b64 takes its address from T+0 at dispatch time, not at EXEC time
     (`*(u32 *)(S - 0x1000)` inside FUN_00003b64, executed from FUN_00002db8).
  3. Therefore, once the host has written address A to T+0 via OUT 0x20 and has
     not changed it again, every subsequent write to S+4 is content(A).
  4. So if the host observes S+4 via 0xaa *before* setting A, obtaining a
     baseline B, and later observes a value V != B, then S+4 was written after
     A was set, hence V == content(A).

That inference uses no timing assumption and no unexposed state. Its one gap is
V == B, i.e. content(A) happens to equal the last observed buffer -- common in
padding runs. The tool resolves that by re-basing: drive S+4 to an anchor chunk
whose content is already proven and differs from B, then repeat. One usable
anchor is sufficient, because content(A) cannot equal two different values. If
no anchor is available yet the dump aborts rather than accept unproven bytes.

Also verified and used:
  * the status error byte IS trustworthy for the EXEC's own verdict, because it
    is written by the same interrupt-context parser that consumed the EXEC
    report, before any later report can be processed (0x00003984 range,
    0x00003964 length, 0x00003938/0x000039ea lock).
  * the READ-busy bit retains one legitimate use: FUN_00003b64 does NOT mask
    interrupts (unlike FUN_00003ab8 and FUN_00003afc, which both bracket
    themselves with cpsid/cpsie), so the USB responder can observe a
    half-written S+4. The handshake skips the 0xaa fetch while bit 1 is set.
  * the flash engine requires 4-byte alignment of address, destination, and
    length (FUN_00002f0c: `(*param_2 & 3)`, `(param_2[4] & 3)`,
    `(param_2[0xc] & 3)`). Chunk addresses are multiples of 0x30 and the length
    is 0x30, so both are aligned; the destination S+4 = 0x18012a90 is aligned.
  * the status flags byte exposes bit 7 (unlocked) and bit 0 (erase/program in
    progress); the tool now aborts on either, since a read-only dump has no
    business proceeding against an unlocked or mid-write bootloader.

=== 7. FACT CLASSIFICATION ===
VERIFIED (instruction-level, this image)
  * S/T/W absolute addresses and the field layout, cross-checked three ways.
  * The complete reader/writer set for S+0x34, S+0x35, S+0x36, S+0x38, S+0x39,
    the busy bit, and the S+4 response buffer.
  * The 0x1f parser's pending gate at 0x000038de, and that a dropped EXEC

  * The 0x1f parser sets S+0x34 and W+4 and never W+0.
  * FUN_00002db8 is reachable only from FUN_00003a7c; its body order is
    busy-set, transfer, busy-clear, pending-clear.
  * FUN_00003a7c's loop body is gated on W+0, tested before any body execution.
  * The SysTick handler at 0x000048d0 is the only writer of W+0.
  * main() is FUN_00007ec8 and its whole loop is `do { FUN_00003a7c(); } while(1)`.
  * SysTick is enabled with a static reload of 161999.
  * 0x8f returns S+0x38 and S+0x35; 0xaa returns S+4 for S+0x36 bytes; neither

  * The vendor-HID router runs in USB-interrupt context. The evidence: it is
