ASUS ROG Falchion Ace HFX — bootloader split-channel correction
Date: 2026-09-02 America/Mexico_City

PURPOSE
Resolve the timeout from the separately authorized minimal bootloader
status/zero-buffer probe, correct the host tools, and record the exact live
boundary. This log does not authorize or perform another live probe.

LIVE EVENT BEFORE THE CORRECTION
The owner changed the FF01 node ACL manually and explicitly authorized the
minimal four-report probe. The then-current tool selected /dev/hidraw6 and
opened that single FF01 node for both writes and reads.

Command:
  python3 tool/probe_bootloader.py --run --acknowledge-volatile-length

Material captured output:
  validated_node=/dev/hidraw6
  action=4 exact reports; 3 queries + volatile set-length; no flash access
  ABORT: no response report within 2s

The equality guard advances only after a successful transport.write(). The
timeout therefore proves the tool wrote exactly report 1 and stopped:
  8f 00 00 ... 00   (64-byte status query payload)
Linux hidraw prepended the unnumbered-report placeholder 00, for 65 bytes total.

It did NOT send report 2 (0x21 set volatile length), report 3 (0xaa buffer
query), report 4 (second 0x8f), an address, execute-READ, unlock, erase,
program, reset, or any SPI operation. No flash access occurred.

WHY THE RESPONSE TIMED OUT
Log 82 found the FF01 descriptor but treated descriptor presence as proof that
one FF01 hidraw node carried both directions. That inference was insufficient.
Read-only bootloader instruction analysis establishes distinct controller
channels:

  - FUN_0000bd40 is the vendor-HID router. Its receive call is
    FUN_0000aff0(..., channel=callback_arg).
  - FUN_000076ac is the physical OUT callback and invokes the registered router
    on OUT channel 0.
  - FUN_00004f7c sends responder output through FUN_0000aec8(..., channel=1, 0).
  - FUN_0000a5c0 initializes IN channels in order EP1, EP5, EPC, EPE and OUT
    channels in order EP6, EPD, EPF.
  - The handler table at 0x00006bf8 contains four IN handlers followed by three
    OUT handlers, matching those channel indices.

Therefore:
  command write: OUT channel 0 -> EP6 -> interface 0 -> usage page FF01
  response read: IN channel 1  -> EP5 -> interface 1 -> usage page FF00

The first status reply was expected on FF00. Because the tool had not opened
that hidraw input queue, it could not capture the reply. The timeout is evidence
against single-node routing, not evidence that the bootloader ignored 0x8f.

FAILED/REJECTED INVESTIGATIONS RETAINED FOR AUDITABILITY
  - The first custom decoder read an extended match count after literals; the
    ARM instructions read both extended counts before copying literals. The bad
    decoder was rejected.
  - A generic third-party scatterloader count interpretation did not reproduce
    the firmware and was rejected; the final decoder follows the actual ARM.
  - A sandboxed Ghidra run could not create/read its normal user configuration
    directory and exited before analysis. The direct rerun succeeded with
    -readOnly -noanalysis.
  - One quoted-search command accidentally allowed shell backtick substitution
    and tried to run a harmless nonexistent command named 0xFF01. It changed no
    file or device.

SAFETY RESULT
During the correction work, no /dev/hidraw node was opened for protocol I/O and
no HID/USB report was transmitted. There was no reset, driver detach, permission
change by the assistant, unlock, set-address, execute-READ, erase, program,
update, or SPI command. The only bootloader protocol report sent in this phase
remains the single previously authorized 0x8f status query described above.
