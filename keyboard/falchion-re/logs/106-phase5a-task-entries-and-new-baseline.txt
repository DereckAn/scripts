STEP 3 — HARVESTING CALL SITES BY DATA-FLOW
================================================================================
Added ghidra/scripts/FalchionTaskCreation.java. It resolves arguments with
Ghidra constant propagation over the CALLING function — not by reading bytes
near the call. r0-r3 are read at the call instruction. Arguments five and six
live on the stack under AAPCS, so the script scans backwards inside the caller
for the last `str <reg>,[sp,#off]` at that offset and resolves <reg> there.

TWO THINGS THE FIRST VERSION GOT WRONG, both fixed and both worth recording:
  - It missed `strd Ra,Rb,[sp,#0]`, which writes Ra at 0 and Rb at 4. INIT_TASK
    is created with exactly that instruction (`18000070 strd r0,r1,[sp,#0x0]`),
    so a5 came back `unknown` on every site. A slot reached only by the second
    half of a strd is now resolved from operand 1. Before: resolved=0 of 5.
    After: resolved=5 of 5.
  - It reported `valid_subroutine` alone. PseudoDisassembler.isValidSubroutine
    returns FALSE for every one of these targets, because the span is still
    stored as undefined data before it is seeded — which is true of every
    target worth seeding. Requiring it would have rejected all five real
    tasks. The script now also decodes forward from the address and reports
    how many instructions decode and what the first one is, and acceptance
    uses that. `valid_subroutine` is still printed so the disagreement is
    visible rather than hidden.

FIRST HARVEST — before main existed as a function, only one call site was
visible, because a call from an undisassembled region produces no reference:
  PRIMITIVE entry=18012fa4 name=FUN_18012fa4 body=18012fa4..18012ff9 callers=1
  CALLSITE ... instr=18015e5e func=18015cb6 ... str=usbd_wdt

STEP 11 — DETERMINISM AND FAIL-CLOSED TESTS
================================================================================
Added tool/harvest_task_entries.py and tool/test_harvest_task_entries.py
(22 tests). Acceptance is conservative: a call site becomes a root only when
EVERY argument resolved, the entry carries the Thumb bit, it lies inside one of
the two images, and its bytes decoded as Thumb. Everything else is recorded
unresolved and reported, never guessed and never dropped.

Each of these is asserted to REJECT:
  - an unresolvable argument rejects the call site (`stack_words` unresolved)
  - an unresolvable entry rejects it and assigns no program
  - an entry without the Thumb bit is rejected — the frame builder takes it
    straight as the task PC, so an even value would fault immediately
  - an entry outside every image is rejected
  - an entry with no TARGET line is rejected: nothing checked that it decodes
  - a target that decoded only 2 instructions is rejected
  - an unmapped target is rejected
  - a call site in no function yields six unresolved arguments and no root
  - a CALLSITE line with the WRONG ARITY is not parsed as a call site at all,
