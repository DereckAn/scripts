STEP 1 — EVERY HOST REPORT DESCRIPTOR IS IN THE REGION, BYTE FOR BYTE
================================================================================
The four report descriptors the host read back (log 09) were searched for in
every preserved image. Each is found exactly once, in the reconstructed
decompressed region, and nowhere else:

  hidraw0 (68 B)  region +0x0008    app: not found   entry: not found
  hidraw1 (34 B)  region +0x004c    app: not found   entry: not found
  hidraw2 (182 B) region +0x006e    app: not found   entry: not found
  hidraw3 (23 B)  region +0x0124    app: not found   entry: not found
  identical offsets in the vendor region

The fifth (interface 4, LampArray, 327 B) was not captured to log 09, so it was
located structurally: it begins at +0x13b, immediately after hidraw3, and its
first bytes are

  +0x13b  05 59 09 01 a1 01 85 01 09 02 a1 02 09 03 15 00 27 ff ff 00 00 75 10 95

which is exactly the item sequence notes/usb-descriptors.txt records for it
(Usage Page 0x59, Usage 1, Collection Application, Report ID 1, Usage 2,
Collection Logical, Usage 3, Logical Min 0, Logical Max 65535, Report Size 16).
It ends at +0x282 with `b1 02 c0 c0` — Feature, End Collection, End Collection —
and 0x282 - 0x13b = 327, the host's wDescriptorLength.

So all five report descriptors are stored verbatim and contiguously at
+0x008..+0x282.

STEP 4 — THE CONFIGURATION DESCRIPTOR IS BUILT, AND THE ARITHMETIC PROVES IT
================================================================================
FUN_18018082, decompiled read-only, opens with:

  for (iVar5 = 0; iVar5 < (int)(uint)*(byte *)(DAT_18018390 + 0x12); iVar5++) {
    uVar8  = (uint)*(byte *)(DAT_18018390 + iVar5 * 0x18 + 0x16);
    iVar10 = (uVar8 & 1) - ((int)(uVar8 << 0x1e) >> 0x1f);      <- bit0 + bit1
    iVar7  = iVar7  + iVar10 * 7 + 0x12;                        <- byte total
    iVar11 = iVar11 + iVar10 + 2;                               <- chunk count
  }
  piVar6 = (int *)thunk_EXT_FUN_000019d0(iVar11 * 4 + 4 + iVar7);   <- malloc

  DAT_18018390 = 0x1803435c, the RAM copy of the table.

That is: 0x12 bytes per interface (9 interface + 9 HID class) plus 7 per
endpoint, exactly the standard sizes, driven by the same 0x18 stride and the
same +0x16 flag byte. Recomputing it from the table:

  iface  flags  endpoints  bytes
    0     0x01      1      0x12 + 7  = 25
    1     0x03      2      0x12 + 14 = 32
    2     0x01      1      0x12 + 7  = 25
    3     0x01      1      0x12 + 7  = 25
    4     0x02      1      0x12 + 7  = 25
  plus the 9-byte configuration header                       = 141 = 0x008d

$ python3 tool/map_usb_routing.py
  PASS wTotalLength recomputed from the table equals the host's — built 141 (0x8d) vs host 141

The host observed wTotalLength 0x008d. The firmware stores no such bytes; the
arithmetic that produces them was read out of the builder's instructions. This
is what "constructed at runtime" is asserted on.

The interface-4 record's flags are 0x02 — the only record with bit1 set and
bit0 clear, i.e. OUT-only — which is exactly the host's OUT-only interface 4.

Strings are stored as plain ASCII ("ASUSTeK" at +0x850, "ROG FALCHION ACE HFX"
at +0x882, "hid driver" at +0x8ec, "Sonix HID" at +0x9a4) with the LANGID dword
0x00000409 at +0x848. A USB string descriptor is UTF-16LE with a 2-byte header,
so these are inputs to a builder, not descriptors.

STEP 6 — 0x40100000 IS THE USB DEVICE CONTROLLER, NAMED BY THE FIRMWARE
================================================================================
The block was carried as unnamed from log 100. It is now named, and NOT by
correlation — by the firmware's own strings.

$ inventory strings of every function that accesses 0x401xxxxx
  0x18016f6e Vector_IRQ6   {'send\susbd_ep0_Queue\serror\n', 'send\susbd_irq_Queue\serror\n'}
  0x18008c16 FUN_18008c16  {'USB_PM_Rs','USB_PM_Ct','USB_PM_Rn','PM_nRs','PM_nNRs','Wake-up','Enter\ssleep','USB_Demo_Mode'}
  0x18015ce2 FUN_18015ce2  {'usbd_wdt'}

IRQ6's handler contains the firmware's own name for the two queues it feeds:
usbd_ep0_Queue (control endpoint) and usbd_irq_Queue. FUN_18008c16 is USB power
management. FUN_18015ce2 is, from log 106, the function that creates the task
named "usbd_wdt" — the USB device watchdog — and it also writes this block.

REGISTER BASE. Vector_IRQ6 loads its base from a literal:
  *(0x1801723c) = 0x40100018
and every 0x401xxxxx target the Phase 5 census attributes to IRQ6 is that base
plus a small displacement, with no leftovers:
  base-0x04 = 0x40100014   base+0x04 = 0x4010001c   base+0x14 = 0x4010002c
  base+0x68 = 0x40100080   base+0x6c = 0x40100084
It also loads *(0x18017240) = 0xe000ed04 (ICSR) with 0x10000000 (PENDSVSET), so
the handler ends by pending PendSV — it hands off to the scheduler rather than
doing work in interrupt context.

BOTH DIRECTIONS.
  init -> handler: 27 functions touch the block, clustered at
    0x180146ec..0x180171c8 plus 0x18008b56..0x18008c16. Vector_IRQ6 is the only
    interrupt among them.
  handler -> consumers: Vector_IRQ6 calls FUN_18012b0c and FUN_18012bc6, both in
    the RTOS range and both with no MMIO of their own, then pends PendSV. Its
    two error strings name the queues, so the handler's output is two RTOS
    queue posts, consumed by a task.

WHY THE CORE AND THE DRIVER SHOW NO CALL PATH. A breadth-first search from
FUN_18018bd6, FUN_180171b0 and FUN_18017672 reaches NO function that accesses
0x401xxxxx. That is not a gap in the evidence — it is the architecture. The two
layers are joined by the function-pointer tables 5A recovered:
  table 0x18018ce8 (12 entries) — every target is a USB core/descriptor
    function, including the builder FUN_18018082 and FUN_18017f9a
  table 0x18016d44 (26 entries) — every target is in the controller-driver
    cluster, including FUN_18016104, FUN_1801533c, FUN_180158de
  table 0x18017d08 (6 entries) — a third layer between them
The call is indirect through these tables, which is exactly why 5A had to seed
them before this step could read anything.

STEP 7 — THE VENDOR CHANNEL, RECEIVE AND TRANSMIT
================================================================================
RECEIVE — EP 0x0d OUT -> buffer -> dispatcher.

A value cross-reference over the whole application image finds exactly TWO
functions that touch the buffer 0x180233a8: the producer and the dispatcher.

  FUN_18000aec, called by FUN_18016104 (an entry in the driver ops table
  0x18016d44, and itself a 0x40100000 accessor):

    void FUN_18000aec(undefined4 param_1,uint param_2)
    {
      pcVar1 = DAT_18000e64;                       /* 0x180233a8 */
      if ((*DAT_18000e64 == '\0') && (4 < param_2)) {
        if (0x3f < param_2) {
          thunk_EXT_FUN_0000262a(DAT_18000e64,param_1,0x40);      /* memcpy 64 */
          return;
        }
        thunk_EXT_FUN_0000262a(DAT_18000e64,param_1,param_2);     /* memcpy len */
        thunk_EXT_FUN_00002728(pcVar1 + param_2,0x40 - param_2);  /* memset 0 */
        return;
      }
      return;
    }

  OWNERSHIP: byte 0 of the buffer is both the command byte and the busy flag.
  The producer copies only when it is zero. A packet arriving while the previous
  one is unprocessed is DROPPED SILENTLY — there is no else branch, no error
  path, no counter and no second slot.
  SIZE: packets of 4 bytes or fewer are rejected; longer ones are truncated to
  64; shorter ones are zero-padded to 64. The buffer is always a full frame.
  DMA: none is visible at this level. The transfer into the buffer is a CPU
  memcpy from a caller-supplied pointer.

  FUN_18001fbe (the dispatcher) then opens with
    18001fbe  push {r0,r1,r2,r3,r4,r5,r6,r7,r8,r9,r10,r11,r12,lr}
    18001fc2  ldr  r4,[0x18002174]        ; *(0x18002174) = 0x180233a8
    18001fc4  ldrb r0,[r4,#0x0]
    18001fc6  cmp  r0,#0x0
    18001fc8  beq  0x180020bc             ; nothing to do
  the exact complement of the producer's gate.

TRANSMIT — dispatcher -> SendResponse64 -> EP 0x85 IN.

  FUN_18000a70 (VendorHID_SendResponse64), callers FUN_18000ad8, FUN_18000d56
  and the dispatcher FUN_18001fbe:

    void FUN_18000a70(param_1,param_2,param_3,param_4,uint param_5)
    {
      thunk_EXT_FUN_0000276c(&local_58,0x40);     /* memset 64 */
      thunk_EXT_FUN_0000276c(&local_98,0x40);     /* memset 64 */
      if (0x3c < param_5) { param_5 = 0x3c; }     /* clamp payload to 60 */
      local_56 = (undefined2)param_3;  local_58 = param_1;  local_57 = param_2;
      thunk_EXT_FUN_0000262a(auStack_54,param_4,param_5);
      local_96 = (undefined1)param_3;
      local_95 = (undefined1)((uint)param_3 >> 8);
      local_98 = param_1;  local_97 = param_2;
      thunk_EXT_FUN_0000262a(auStack_94,param_4,param_5);
      FUN_18018bd6(1,&local_98,0x40,0);
    }

  WIRE FORMAT: 4 header bytes (param_1, param_2, param_3 as a 16-bit field) plus
  a payload clamped to 0x3c = 60, in a 64-byte frame zero-filled first.
  OBSERVED ODDITY, recorded not explained: two identical 64-byte frames are
  built on the stack and only the second is sent. The first is dead as written.

  FUN_18018bd6(interface, buffer, length, flags), listing confirmed:
    18018bdc  ldr  r1,[0x18018cd0]     ; USB core struct 0x1801ebb8
    18018be0  add.w r7,r0,r0,lsl #0x1  ; r7 = interface * 3
    18018be4  ldr  r1,[r1,#0x4]
    18018be8  add.w r2,r1,r7,lsl #0x3  ; + interface * 0x18   <- same stride
    18018bec  ldr  r4,[r2,#0x7c]       ; endpoint object
    18018bf0  ldr  r6,[0x18018cd4]     ; table RAM copy 0x1803435c
    18018bf2  ldrb r2,[r6,#0x12]       ; bNumInterfaces
    18018bf4  cmp  r2,r0
    18018bf6  bls  0x18018c12          ; -> return -0x16 (EINVAL)
    18018bfc  ldrb r0,[r4,#0x0]        ; endpoint state
    18018c02  cbz  r0,0x18018c64       ; -> return -5
    18018c06  cmp  r0,#0x1
    18018c08  beq  0x18018c18          ; only state 1 proceeds
    18018c0a  mvn  r0,#0xf             ; -> return -0x10 (EBUSY)
    18018c24  add.w r0,r6,r7,lsl #0x3
    18018c28  ldrh r2,[r0,#0x18]       ; the record's IN wMaxPacketSize
    18018c2a  cmp  r2,r5               ; bounded against the requested length

  COMPLETION AND ERROR HANDLING: three distinct negative returns — -0x16 for an
  interface index at or beyond bNumInterfaces, -5 for an endpoint that is not
  open, -0x10 for one that is busy. FUN_18000a70 IGNORES all three: it does not
  read the return value, so a dropped response is invisible to the vendor
  command layer.

  The `ldrh r2,[r0,#0x18]` is the same field the descriptor builder turns into
  the endpoint's wMaxPacketSize. The transmit path and the enumerated descriptor
  are bounded by one value in one table. Interface index 1 selects the record
  whose IN wMaxPacketSize is 0x40 — endpoint 0x85.

MINIMAL USB-KEYBOARD PATH: EP 0x00 and EP 0x81 — the control endpoint and
interface 0's 8-byte boot report. Everything else is compatibility:
  interface 1 (vendor 0xFF00)  — the ASUS configuration channel; omitting it
      loses vendor software support and, note, the bootloader-entry command
      path recorded in logs 82/87/88 lives on this channel
  interface 2 (consumer/system) — media keys and system controls
  interface 3 (NKRO)           — n-key rollover beyond the boot report's 6
  interface 4 (LampArray)      — per-key lighting through the standard HID
      LampArray page
The parameter table makes each of these a matter of one record and one
bNumInterfaces byte, both of which the firmware validates at 1..5.

WHAT "context" DOES AND DOES NOT MEAN. Each context above is a call-graph and
data-flow statement. It is NOT timing: nothing here observed the device, an
interrupt firing, or a task running.


================================================================================
STEP 9 — REMAINING UNRESOLVED BOUNDARIES
================================================================================
Stated precisely, not closed.

  1. bEndpointAddress. None of 0x81, 0x85, 0x0d, 0x8c, 0x8e, 0x0f is in the
     parameter table, and the byte pair `85 0d` and triple `81 8c 8e` appear in
     no preserved image. The addresses are assigned somewhere this step did not
     find: most likely computed by the builder from an interface/endpoint index,
     or fixed by the controller's endpoint hardware. HYPOTHESIS, not traced.
  2. The OUT endpoints' bInterval. Both are 4 on the host; the table carries one
     interval byte per interface and it tracks the IN endpoint. UNRESOLVED.
  3. iSerial. The device descriptor reports iSerial 2, and lsusb shows it blank.
     No serial string was located in the region. UNRESOLVED.
  4. The producers of the interface 0, 2 and 3 reports. Those are the key-scan
     and media paths — 5C's and 5D's subjects. NOT TRACED HERE, by scope.
  5. The lighting consumer behind EP 0x0f. NOT TRACED HERE, by scope.
  6. FUN_18000a70 builds two identical 64-byte frames and sends one. RECORDED,
     unexplained.
  7. The searches in steps 1 and 2 cover the five preserved images. A mask ROM,
     if one exists, was not searched and cannot be. Nothing here rules out a ROM
     contribution; equally, nothing requires one — the builder recovered in step
     4 accounts for every standard descriptor field except item 1.
