================================================================================
THE HEADLINE
================================================================================
LOG 133 MADE THE PROOF PATH-SENSITIVE AND LEFT IT ALIAS-BLIND. An installation
was invalidated only by a later store carrying the SAME abstract
(object identity, field) pair — but two different identities can name one
physical word, and one identity can be written through two different
expressions. Both shapes let a store that provably destroys the installed
function pointer leave the proof standing.

Both were reproduced before anything was changed. Both are now rejected. No
real reachability number moved, because the real images still prove nothing.

================================================================================
ROOT CAUSE
================================================================================
`_install_transfer()` invalidated a live installation with

    out = {record for record in live
           if not (record.obj == obj and record.field == offset)}

plus one narrow extra rule for a store landing on the word a `("mem", A)`
identity had been read from. That treats the abstract identity as if it were
the address. It is not: an identity is a NAME for an address, several names can
denote one address, and a MEM name denotes an address that is not statically
known at all.


================================================================================
THE ALIAS RULES IMPLEMENTED
================================================================================
Two new helpers with documented rules and their own unit tests. Neither
mentions any synthetic address.

  INSTALL_WIDTH = 4                    a function pointer is one 32-bit word

  effective_range(obj, field, width)
      ("abs", A) + f  ->  the concrete byte interval [A+f, A+f+width)
      ("mem", S) + f  ->  None. A MEM identity is "whatever pointer was read
                          from slot S", which is not a static address.

  may_alias(left, left_field, right, right_field, width)
      1. ABS vs ABS — both intervals concrete: alias exactly when the byte
         ranges OVERLAP. Overlap, not equality, so `("abs",X)+4` and
         `("abs",X+4)+0` collide, and so does a partially overlapping or
         unaligned store.
      2. ABS vs MEM, either way round — a pointer read from a slot can point
         anywhere, including at that absolute object. MAY ALIAS.
      3. MEM vs MEM — two different slots can hold the same pointer, and the
         same slot certainly does. MAY ALIAS whether the slots match or not.

  slot_overwritten(install_obj, store_obj, store_field, width)
      A store whose interval overlaps [S, S+width) invalidates every
      installation derived from slot S, because the pointer itself has
      changed. An unplaceable store invalidates all of them.

CONSEQUENCE, STATED PLAINLY. Rules 2 and 3 mean a MEM-derived installation
survives NO resolved store at all. This is the fail-closed choice the
correction called for: the interpreter cannot prove two runtime pointers
distinct, so it does not try. A MEM installation can still be proven when
nothing is stored between the install and the dispatch, which is the one
positive control it had.

`slot_overwritten` is kept as a separate rule even though `may_alias` already
subsumes it under rules 2 and 3. It is a different reason for a different
fact, it is directly testable, and it stays correct if the alias rules are ever
tightened.

The store also still has to be RESOLVED. Calls, byte and halfword stores,
register-offset and stack stores, multiple-stores, and anything the decoder
does not recognise continue to empty the live set outright — unchanged from
log 133.

================================================================================
REGRESSION TESTS ADDED
================================================================================
class AliasRules — the predicate on its own, no image involved:
  * an ABS identity has a concrete four-byte interval; a MEM identity has none
  * `("abs",X)+4` and `("abs",X+4)+0` alias, in both argument orders
  * partially overlapping words alias (+2 and +6 against +4)
  * adjacent and distant words do not alias (+0 vs +4, +4 vs +8, X vs Y)
  * ABS vs MEM always may-alias, in both orders
  * MEM vs MEM always may-alias, same slot or not
  * a store overlapping the slot invalidates its MEM installs, including a
    partial overlap; a store past the slot does not
  * `slot_overwritten` never applies to an ABS install
  * an unplaceable store overwrites any slot

class Aliasing — the same rules through the real analyser:
   1. ABS install overwritten through a MEM alias            -> no proof, no root
   2. MEM install overwritten through an ABS alias           -> no proof, no root
   3. two ABS expressions for one effective address          -> no proof, no root
   4. a partially overlapping absolute store                 -> no proof, no root
   5. two provably disjoint absolute stores                  -> PROOF PRESERVED
   6. a store directly to the pointer slot                   -> no proof, no root
   7. a store through a DIFFERENT MEM slot                   -> no proof, no root
   8. a store through the SAME MEM slot at another field     -> no proof, no root
   9. the untouched-MEM positive control                     -> PROOF PRESERVED
  10. `len(rooted) == len(proven)` across five shapes

Every positive case asserts the EXACT install instruction, dispatch
instruction, function entry, object identity and field — not a count:

    case 5:  entry 0x18000100, install 0x18000004, dispatch 0x1800000e,
             function 0x18000000, object ('abs', 0x18000200), field 0x0
    case 9:  entry 0x18000100, object ('mem', 0x18000110), field 0x0,
             function 0x18000000

Log 133's mutually exclusive branch reproduction, its straight-line positive
control, its call and unresolved-write invalidations, and the hardware-map
partial-table integration tests all still run and still pass.
