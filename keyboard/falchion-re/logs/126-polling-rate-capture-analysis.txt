================================================================================
STEP 4 — THE MEASUREMENT: WHICH INDEX IS WHICH, FROM THE WIRE
================================================================================
THE PROBLEM. With no wall-clock stamps, "index 0 is 1000 Hz" would otherwise
rest entirely on the owner remembering that they started at 1000 — which is
exactly the kind of anchor the prompt's fallback clause allows but which cannot
carry a protocol document.

THE METHOD. A high-speed interrupt IN endpoint with bInterval = 1 is polled
every 125 us; a full-speed one can only complete on a 1 ms frame boundary. A
device that only has a new report ready every millisecond can therefore only
complete on the coarser grid even when the host offers the finer one. So: take
the gap between consecutive key reports, never crossing a rate change, and ask
how close it sits to a multiple of 1.000 ms and of 0.125 ms. The measure is a
PHASE, so it is independent of how fast the owner was typing.

The owner was typing "1 2 3" repeatedly with rollover — payloads 0x1e, 0x1f,
0x20 plus space and backspace — which supplies gaps short enough to matter.

$ python3 tool/map_polling_rate_protocol.py   (measurement section)
  EP 0x81 index 0:  121 gaps,  85.1% on the 1 ms grid,  90.9% on the 125 us grid
  EP 0x81 index 3:  229 gaps,  12.2% on the 1 ms grid,  90.0% on the 125 us grid
  EP 0x8c index 0:  121 gaps,  82.6% on the 1 ms grid,  83.5% on the 125 us grid
  EP 0x8c index 3:  229 gaps,  13.1% on the 1 ms grid,  88.6% on the 125 us grid

  Acceptance windows are a tenth of each grid: 50 us of a millisecond, 12.5 us
  of 125 us. By chance a uniform distribution would land inside them 10% and
  20% of the time.

  INDEX 0 SITS ON THE MILLISECOND GRID: 85% against a 10% chance level, and the
  mean distance to the grid is 22 us where uniform would be 250 us.
  INDEX 3 DOES NOT: 12.2%, i.e. chance, with a mean distance of 249 us — but
  90% of the same gaps sit within 12.5 us of a 125 us multiple.
  The 1 ms grid is a SUBSET of the 125 us grid, so index 0 satisfies both; the
  discriminator is the 1 ms test, and it separates the states by seven to one.

  TWO INDEPENDENT ENDPOINTS AGREE — interface 0's 8-byte boot report and
  interface 2's 21-byte vendor event report — and both read
  index 0 = 1000 Hz, index 3 = 8000 Hz.

  PER WINDOW, so the result is not carried by one burst (EP 0x81):
    window  3  0x00   16 gaps   62.5% on the 1 ms grid
    window  4  0x03  121 gaps   14.9%
    window  5  0x00  105 gaps   88.6%
    window  6  0x03   65 gaps   10.8%
    window 12  0x03   43 gaps    7.0%
    (the other seven windows contain no typing and are silent — recorded, not
     filled in)
  Each value's reading recurs, and the two groups do not overlap.

WHAT THIS ALSO PROVES: HIGH SPEED. Gaps of 1.752, 2.120 and 2.876 ms occur in
index 3. On a full-speed bus, where the host polls a bInterval=1 interrupt
endpoint once per 1 ms frame, a non-integer-millisecond gap between two
completions cannot happen — and split transactions through a high-speed hub
would still land on frame boundaries. LOG 107's high-speed reading, which log
124 flagged as inherited rather than derived, IS NOW DERIVED FROM THE WIRE.

ANTI-VACUITY, because the whole argument is a difference between two numbers:
the grid predicate is fed a synthetic 1 ms train and required to accept it, and
a synthetic 125 us train and required to REJECT it on the millisecond grid while

THE DISPATCH PATH, from the vendor-HID dispatcher FUN_18001fbe:
  18001fbe  push {...}

                                      ; request buffer, log 107's exactly
  18001fd6  movs r6,#0x1              ; r6 = 1, set ONCE, at entry
  1800201c  cmp  r2,#0x51             ; r2 = request byte 0
  1800201e  bne  ...

  180024d2  cmp  r2,#0x31
  180024d4  beq  0x180025c6  ->  b 0x18002b2e
  r6 IS NOT REASSIGNED ON THIS PATH: the branch chain is 18001ff2 -> 18002014
  -> 18002020 -> 1800248e -> 180024ba -> 180024d2, and none of those
  instructions writes r6. That matters, because r6 is the shift base.

THE HANDLER, 0x18002b2e:
  18002b2e  ldrb   r1,[r4,#0x4]       ; REQUEST BYTE 4 — the index
  18002b30  cmp    r1,#0x3

  18002b4e  ldr    r1,[0x18002e44]    ; *(0x18002e44) = 0x1801e736

  18002b58  adds   r3,r4,#0x4
  18002b5a  movs   r2,#0x0

     0x18002e48  = "=S_PR_U\0"  — the firmware NAMES THE COMMAND. The prefix
                   convention matches log 120's "R_NSK_M" and log 125's
                   "PS_*/PR_*" tags. Read as Set_Polling_Rate_Update. This is

                   of 3 and the profile-block store.

  THE RESPONSE IS EXPLAINED, not just matched. Log 107 recovered
  FUN_18000a70(a,b,c,buf,len) as: byte 0 = a, byte 1 = b, bytes 2..3 = c as a
  u16, then len payload bytes from buf, in a 64-byte zero-filled frame. Here
  a = 0x51, b = 0x31, c = 0, buf = &request[4], len = r6 = 1. That produces
    51 31 00 00 <request byte 4> 00 ... 00
  which is EXACTLY the 64-byte reply on the wire. The "verbatim echo" is
  therefore not a memcpy of the request — it is a reconstruction that happens to
  coincide, and the coincidence is the confirmation.

THE ACCEPTANCE BOUND, and what it does and does not support.
  The handler accepts 0 and 3 by explicit comparison and falls through for
  EVERYTHING ELSE, INCLUDING 1 AND 2. So the four-wide reading does NOT rest on
  the handler accepting 1 or 2 — it does not. It rests on three independent
  pieces of the same instruction stream: bfi writes a FOUR-BIT field; the
  reload path masks with 0xf; and the expansion is `1 << index`, whose useful
  range is 0..3 for a byte destination holding 1, 2, 4 or 8.
  1 << 0 = 1, 1 << 1 = 2, 1 << 2 = 4, 1 << 3 = 8. Step 4 measured index 0 as
  1000 Hz and index 3 as 8000 Hz, so THE UNIT OF THE MULTIPLIER IS 1000 Hz,
  and indices 1 and 2 are 2000 and 4000 Hz BY ARITHMETIC. Derived. Not observed.
  Labelled `derived_not_observed` in the JSON and "not observed" in the
  Markdown, with a test that requires the labelling to be there.

PERSISTENCE — AND A REFINEMENT TO LOG 125.
  The field is PROFILE BLOCK +0x4f8, BITS 0..3. Log 125 recorded +0x4f8 as
  "VERSION STAMP, copied from ROM 0x1801bfbc". That reading is REFINED, not
  withdrawn: the halfword at +0x4f8 holds the version stamp AND, in its low four
  bits, the polling-rate index. Log 125's own accounting is what makes this
  consistent — the field is covered by NEITHER checksum (checksum A runs
  +0x002..+0x4b1, checksum B runs +0x4fc..+0x7bb), so writing four bits of it
  does not invalidate either sum.
  AND IT CLOSES ONE OF LOG 125's THREE UNMATCHED ROWS. Log 125 left `speed`,
  `customPattern` and `pollingRate` unmatched between the Armoury Crate decode
  and the firmware's format. `pollingRate` is now matched: it is profile block
  +0x4f8 bits 0..3, and since index 3 measures as 8000 Hz,
  notes/ac-profile3-decoded.json's `"pollingRate": "3"` MEANS 8000 Hz.

  THE RELOAD PATH proves it survives storage. FUN_18000d56 — log 125's storage
  state machine — at 0x1800153a:
    18001536  ldr    r2,[pc,...]      ; 0x1801e736
    18001538  strb   r0,[r1]
    1800153a  ldrb.w r1,[r7,#0x4f8]   ; the stored halfword's low byte
    18001540  and    r1,r1,#0xf       ; the same 4-bit mask
    18001544  lsl.w  r1,r0,r1         ; the same 1 << index expansion
    18001548  strb   r1,[r2]          ; into the same byte
  The load path and the wire handler perform IDENTICAL arithmetic into the same
  destination. A field that were merely a version stamp would not be expanded
  through a shift on profile load.

READ-BACK — A COMMAND NOBODY HAD FOUND: `12 15`.
  1800208c  cmp r2,#0x14 / beq 0x1800217c
