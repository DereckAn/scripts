BLOCKER 1 — PROVENANCE. REPRODUCED FIRST
================================================================================
$ a synthetic image with the literal load in function A at 0x18000000..0x08
  and an unrelated store + `blx` in function B at 0x18000020..0x28

  validated 0x18000040 | 2 of 3 entries are loaded by a PC-relative literal
  load inside a real function body; 1 are stored into a structure field that
  `ldr rX,[rY,#off]; blx rX` calls
     consumer 0x18000040 0x18000000 () ()
     consumer 0x18000044 0x18000004 (0,) (0,)
  root targets: ['0x18000010', '0x18000020', '0x18000030']

  TWO FAILURES IN ONE OUTPUT. The load in function A was correlated with a
  store and a call in function B — `pending` and `loaded_from` were module-level
  per-survey dictionaries that no boundary ever cleared. And ONE "dispatched"
  entry rooted ALL THREE targets. The same two faults produced log 131's
  "21 of 26 ... 8 of 12 dispatched", with all 26 and all 12 rooted.

ROOT CAUSE
  * register state survived function and body-range boundaries;
  * registers were not killed on every write, only on the few encodings the
    scanner recognised;
  * the object a field belonged to was not modelled at all — only the offset,
    and 0x0/0x4/0x8/0xc occur in most structures in the image;
  * a table's verdict was a single boolean, so any evidence rooted everything.

THE CORRECTION — tool/find_pointer_tables.py, rewritten analysis
  A per-function fixed-point data-flow pass:
    * one function at a time, starting from an empty register map;
    * a worklist over instructions; at a JOIN the incoming states are MERGED,
      and the merge keeps only what every predecessor agrees on. That is the
      proof: two arms of a branch cannot contribute half a fact each, and two
      arms that DO agree are not thrown away either;
    * every instruction kills its destination register. Encodings whose
      destination the architecture fixes are killed exactly; anything else
      drops the whole map;
    * a function containing a flow instruction whose successors cannot be
      enumerated — TBB, TBH, `BX <reg>`, `IT` — is NOT ANALYSED AT ALL and is
      listed as skipped, because after it neither the joins nor the
      instruction boundaries can be trusted;
    * objects have identities: ("abs", A) for the object at absolute address A,
      ("mem", A) for the object whose pointer was read from A. A store records
      (entry word, object, field); a dispatch records (object, field); they
      match only when BOTH agree.
  THE ONE ASSUMPTION, stated and pinned by a test: AAPCS. r4-r11 survive a
  call; r0-r3, r12 and lr do not. Without it an object base is lost at the
  first `bl` and nothing can be reported as installed at all. It is an
  assumption about compiler-generated code, not a proof, and it never promotes
  anything on its own — rooting still needs the matching object.

FOUR BUCKETS, REPORTED SEPARATELY
  LOADED    an instruction in an analysed body literal-loads the entry
  INSTALLED that value is stored into a named object's field
  PROVEN    that same object's same field is the operand of an indirect call
  ROOTED    proven entries only — unless a WHOLE-TABLE PROOF is printed

WHOLE-TABLE PROOF, defined so it can be argued with. Every entry installed; all
installs naming the SAME object; into DISTINCT fields; from ONE function; and at
least one of those fields indirect-called through that same object. Short of
that, a table roots only its individually proven entries.

WHAT THE INSTALL EVIDENCE ACTUALLY SHOWS, kept because it is real:
  0x18017d08: all six entries stored by FUN_18018b22 into
    object@0x180342c8 + 0x8,0xc,0x10,0x14,0x18,0x1c
  0x18018ce8: all twelve stored by FUN_18018a28 into
    object*@0x1801ebbc + 0xc,0x10,0x14,0x18,0x1c,0x20,0x28,0x38,0x54,0x58,0x5c,0x60
  Twelve distinct fields of one object, from one function, beside the
  `HID Function` string the same function stores at +0x0. That is an operations

  0x18016d44 is worse and says so too: its installer FUN_18016934 contains a

ADVERSARIAL REGRESSION TESTS (tool/test_find_pointer_tables.py, class
Provenance + class Rooting; every one built from hand-assembled Thumb):
  - a load in one function and a store in another do not correlate
  - a store into object X and a call through the same field of object Y do not
  - a register overwritten before the store breaks provenance
  - the object register overwritten before the store breaks it
  - the object register overwritten before the call breaks it
  - the loaded pointer overwritten before the call breaks it
  - two branch arms that DISAGREE are not joined
  - two branch arms that AGREE are joined  (the positive control, so the test

  - a whole-table proof roots every entry and prints its reason
  - a whole-table proof needs distinct fields, and needs one object

ISSUE 5 — snap-config.ps1 LOST JSON SCALAR TYPES. REPRODUCED
================================================================================
  Get-Flat's leaf was `$acc[$prefix] = "$value"`. JSON 1 and "1" both become
  "1"; $true and "True" both become "True". Python was not equivalent either:
  it compared raw values, and in Python `True == 1`.

CORRECTED. Both sides now flatten to a TYPE-TAGGED canonical string:
    null        -> null
    Boolean     -> bool:true / bool:false
    number      -> num:<invariant, integral numbers without a fraction>
    string      -> str:<value>
Python compares canonical() and REPORTS the raw values, so the output still
reads naturally. Object keys are sorted and array indices are part of the path,
so ordering is deterministic. The canonical form is never display formatting.

TESTS: number 1 vs string "1"; Boolean true vs string "true"; Boolean true vs
number 1 (the Python trap, asserted); null vs string "null"; a numeric change;
10 vs 10.0 as the same JSON number; a non-integral number; arrays growing and
shrinking; objects gaining and losing keys; a scalar becoming an object; key
order irrelevant but array order significant.

VALIDATION SCOPE, STATED HONESTLY AND NOT OVERSOLD. PowerShell is not executed
anywhere in this repository. `profile_diff.powershell_drift()` is a TOKEN AND
STRUCTURE CHECK over the script text: it catches the leaf being stringified
again, the canonical tags disappearing, a return to the keyboardButton-only
comparison, or a missing contract field. IT DOES NOT PROVE that Get-Flat and
flatten(), or Get-Canonical and canonical(), agree on any input. That
equivalence is an open Windows-only item and is listed as one in
tools/README.md. The class docstring on the test says the same thing.

ISSUE 6 — THE HAL-TRACE REQUIREMENT CONTRADICTED EXPERIMENT 3
================================================================================
The plan required a HAL trace and a hash for every capture; experiment 3
requires Armoury Crate CLOSED, so there is no producer and the old script only
created its output file when a line arrived.

DESIGN CHOSEN: (B) a deterministic session artifact, always.
tools/haltrace.ps1 now writes its header BEFORE listening — start UTC, start
local, host, user, elevation, DBWIN name, filter flag, duration, and an explicit
clock note — and appends an end UTC and a line count in the finally block. A
zero-event run therefore still produces a file to hash, and the script says so:
"zero events. That is a RESULT, not a failure". The plan records that a
zero-event trace is the EXPECTED outcome of experiment 3 and is itself evidence.
A structural check enforces that the header is written before the wait loop and
that the old no-artifact branch is gone.

CLOCKS, CORRECTED. The plan previously said action timestamps came "from the
same clock the capture uses". They do not. USBPcap frames are stamped by the
capture engine, haltrace lines by the Windows wall clock, and hand-written times
by whatever the operator read. The plan now says so, requires correlation on
ABSOLUTE time (frame.time_epoch / frame.time against the UTC stamps), records
that frame.time_relative cannot be compared across files at all, and requires
every cross-artifact alignment to be treated as approximate and manual. Both
decoders now carry frame.time_epoch so that correlation is possible.

ISSUE 7 — TERMINOLOGY FOR 0x5680
================================================================================
"x87 long doubles" is withdrawn everywhere outside the immutable logs. This is
ARM firmware and an exponent-first library representation does not establish the
x87 native memory layout; no ABI was proven and none was needed.

The wording is now "library-specific extended-precision powers-of-ten records",
with the supporting observations listed separately from the interpretation:
  * five consecutive records, a constant 12 bytes apart;
  * field 0 rises 0x4002, 0x4005, 0x400c, 0x4019, 0x4034 — differences of
    3, 7, 13, 27, i.e. the binary exponents of 10^1, 10^2, 10^4, 10^8, 10^16
    offset by a constant 0x3fff;
  * the remaining eight bytes of each record, read as a normalised fraction,
    give those same five powers of ten;
  * the block sits immediately after the `0123456789ABCDEF@0X` and
    `0123456789abcdef@0x` digit tables a formatted-print routine uses.
All the finding needs is that field 0 is an exponent and not an address.
