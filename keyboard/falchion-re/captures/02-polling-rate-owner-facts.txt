DEVIATION FROM THE PROMPT'S PREMISE — READ BEFORE STEP 2
================================================================================
The prompt assumes four rate changes: 1000 -> 2000 -> 4000 -> 8000.
ARMOURY CRATE 6.5.7.0 ON THIS HOST EXPOSES ONLY TWO VALUES: 1000 Hz and 8000 Hz.
There is no 2000 and no 4000 option in the UI. This is a UI/observation limit,
not a decode failure. See U7: decode what IS there; do not invent four values.

REVISED CAPTURE PLAN (what the wall-clock stamps correspond to)
  CHANGE 1: set 1000
  CHANGE 2: set 8000
  CHANGE 3: set 1000   (repeat of change 1)
  CHANGE 4: set 8000   (repeat of change 2)
Four change events, two distinct values, each value observed TWICE. The repeats
are deliberate: U3 requires that a candidate byte "repeats across at least two
windows" before it is accepted, and this plan supplies that directly.

A TESTABLE PREDICTION THE TWO-VALUE CASE MAKES SHARPER, NOT WEAKER
Whatever byte carries the rate, its two observed values discriminate between the
competing encodings from STEP 2 in one shot:
  0x01 / 0x08          -> Hz/1000
  0xe8 0x03 / 0x40 0x1f -> raw Hz, little-endian 16-bit
  0x00 / 0x01          -> a 2-entry index; AC exposes exactly what firmware has
  0x00 / 0x03          -> a 4-ENTRY index (0..3) with only 0 and 3 reachable
                          from this UI. This would mean the firmware supports
                          four rates while AC exposes two, AND it would make
                          notes/ac-profile3-decoded.json's
                          "performance": {"pollingRate": "3"} mean 8000 Hz.
                          That is the single most informative outcome available
                          from this capture; check for it explicitly.
  descending order (8000 -> 0) is equally possible: see U2, test both directions.
