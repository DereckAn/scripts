# Installed 1.59 hardware and runtime interface map

Generated by `tool/report_phase5.py` from
`tool/map_hardware_interfaces.py`, which combines the vector table
parsed out of Candidate A's own bytes,
`ghidra/scripts/FalchionPeripheralMap.java` (every load and store whose
base register Ghidra's constant propagation resolves), and the call
graph from `ghidra/scripts/FalchionFunctionInventory.java`.

Offline and read-only; no device was accessed and no dump was modified.

## Two rules this map keeps

**Observed behaviour is separated from address-space identity.** There
is no public SNC73270 reference manual in this repository, so an address
space with no positive evidence behind it is classified `unknown` — this
map does not call something a vendor peripheral merely because it is not
anything else. The only names here come from the ARMv7-M architecture,
which applies to any Cortex-M3. Nothing in this map supports a claim
about USB, key scanning, Hall-effect sensing, nonvolatile storage or RGB
hardware.

**Classification is per address, not per block.** The application image
and the RAM above it share a 1 MiB block, and the proven runtime range
ends at `0x18036168` rather than at a block boundary, so labelling a
whole block would manufacture false categories. Blocks whose addresses
have more than one kind are reported as `mixed`.

**Reachability is computed, not assumed.** Each function's context comes
from a breadth-first walk of the call graph out of roots that are
themselves evidence: the vector-table entries, plus the two entry-image
words that point into the application's code. A function no root reaches
is reported as unreached.

## Status of this phase

**first-pass.** This is an MMIO access census plus a decoded vector table. Five of the plan's seven analysis areas are not covered and one is only partial, and the dependency map classifies address spaces rather than the original *services* the exit gate asks about. Phase 5 should be treated as incomplete and partly blocked on a SNC73270 reference manual, not as finished.

## Vector table

- span: logical `0x0..0x140` inside the entry image
- slots: 80 = 16 core + 64 external
- fill value: `0x000014df`, the value repeated across unused slots

An ARMv7-M vector table has **no terminator**, so nothing here looks
for one. The table runs from the image base to the first code address
and every word in between is a slot. The repeated fill value marks a
slot *unused*; it does not end the table, and a live slot can and does
follow it — `IRQ63` at offset `0x13c` holds `0x00000ad1`, a Thumb
pointer to the callerless function at `0x00000ad0`.

## What the values say

Each statement below is a predicate the tool evaluates over the
assembled map, so it is checked rather than asserted, and each carries
its own basis and confidence.

### The NMI handler requests a system reset.

- basis: AIRCR is written 0x05fa0004: the architectural VECTKEY 0x05fa with SYSRESETREQ set. Written from the NMI context.
- confidence: high — the value and the register are both architectural

### The timebase pends a software interrupt, which is the shape of a preemptive scheduler.

- basis: ICSR is written 0x10000000 (PENDSVSET) from the SysTick context, and the PendSV vector points at its own handler.
- confidence: high for the mechanism, none for what the scheduler schedules

### The application also pends that software interrupt, from several sites.

- basis: ICSR is written 16 times in the application image, including from an interrupt context.
- confidence: high for the mechanism

### The interrupts the software enables are the ones the table actually populates: IRQ6, IRQ38.

- basis: NVIC_ISER words written with those bits set, cross-checked against the vector slots that hold a non-default handler. Two independent parts of the image agree.
- confidence: high

### The fault handler reads the architectural fault status and address registers rather than just hanging.

- basis: CFSR, MMFAR and BFAR are all read from the HardFault context.
- confidence: high — all three registers are architectural

### Two identical unnamed blocks are unlocked with a magic key on the reset path.

- basis: 0x40008000 and 0x40009000 are each written 0x5afa0000, and 0x4000800c and 0x4000900c are each written 0x5afa55aa. A key-protected register pair, duplicated. What the blocks control is not established.
- confidence: high for the pattern, none for the identity

### A reset-path register is programmed with the flash address of SN_FWIN record slot 1.

- basis: 0x4002f004 is written 0x60021000, which is exactly record slot 1's address from the installed header. The register is therefore tied to the image layout, whatever else it does.
- confidence: high for the correspondence, none for the register's purpose

### The unnamed block at 0x40100000 is the one the live interrupt serves.

- basis: 19 registers, 126 accesses, touched from IRQ6,called from entry image 0x1994,table@0x18016d44 — that is, from both an interrupt handler and the initialiser the entry image calls. It is the application's principal peripheral. Naming it would require a reference manual.
- confidence: high for the association, none for the identity

### Why each verdict

- **unknown-service**: the original firmware touches this address space and nothing here identifies what it is, so whether a replacement needs it cannot be decided yet. This is a blocked item, not a permission
- **must-reproduce-or-disprove**: every access to this space is on the reset path, so the original firmware programs it before any service exists. That is evidence about the code, not about the address space: a replacement must either do the equivalent or establish that it is unnecessary
- **not-a-service**: RAM inside the proven scatter runtime range
- **may-omit**: reading the mapped flash window is storage access, not a platform service a minimal application has to provide
- **must-replace**: architectural: any firmware that takes an interrupt or keeps time has to program these itself
- **see-registers**: the block holds addresses of more than one kind; read the per-register rows rather than the block

The exit gate asks which original **services** a minimal replacement
must provide. This map cannot answer that, because it classifies
*address spaces* and no vendor address space here is identified. What
it does establish: a replacement must program the ARMv7-M core blocks
itself; the address spaces the reset path programs before any service
exists (`0x40000000`, `0x08000000`, `0x10000000`) must be reproduced or
shown unnecessary; `0x45000000` and `0x40100000` are **blocked** rather
than conditionally permitted, since nothing identifies what they do;
and reading the mapped flash window is storage rather than a platform
service. Treat the gate as partly met and partly blocked on a SNC73270
reference manual.

## Limitations

- Vendor MMIO blocks are described by observed accesses only. This map
  names no vendor peripheral.
- An access appears only when constant propagation resolved its base
  register. Accesses through a pointer held in a parameter or a
  structure are counted as unresolved, so the register list is a lower
  bound rather than a complete set.
- Reachability follows Ghidra's call graph, which does not follow calls
  through function-pointer tables. The application image reports many
  unreached functions for that reason; its task entry points are
  dispatched through tables (logs 48, 49, 65), not called directly.
- Handler functions exist in the analysis only because
  `FalchionSeedVectors.java` created them from the vector table. A raw
  binary import gives Ghidra no reason to disassemble a handler that
  nothing calls.

## Still unresolved

- Any ROM or first-stage condition ahead of the bootloader is unexamined.
- What makes address 0 writable is not established. The bootloader's BootHandoff routine copies 0x10000 bytes from the selected entry to address 0 and then requests a system reset, so a RAM or remap window must be aliased there, but the register that arranges it is unidentified (log 101).
- Which physical keys produce the recovery scan pattern that FUN_000029d4 matches is not established; only the RAM buffer and the matched values are known (log 101).
